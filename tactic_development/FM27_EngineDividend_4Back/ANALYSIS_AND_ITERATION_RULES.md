# FM27 引擎红利四后卫：分析与迭代强制规则

本文件是 `FM27_EngineDividend_4Back` 项目的正式执行规范。凡涉及本项目的赛季数据分析、战术分析、优化、升级、版本对比或 FMF 生成，均须先读取本文件及本目录 README，再按本规范执行。

## 一、触发方式

### 统一触发词
用户说出 **「执行四后卫项目规则」** 时，立即读取并执行本文件。

### 自动触发
即使用户没有说统一触发词，只要任务明显涉及以下任一事项，也必须自动读取本文件：
- 分析赛季数据或赛季报告
- 分析、评估或优化当前四后卫战术
- 升级战术、设计下一版本或生成 FMF
- 对比四后卫战术版本
- 继续 FM27 引擎红利四后卫研发

不得要求用户重复提醒。

## 二、项目范围与资料读取
### 赛季报告入库通知：自动执行流程

以下说法均视为同一个强触发事件，不要求用户使用固定句式：
- “赛季数据报告在仓库了”
- “赛季报告已经上传/提交到 GitHub”
- “我把赛季数据放进仓库了”
- “报告已推送到 fm-ta”
- “可以分析仓库里的赛季报告了”
- 其他明确表达“赛季报告已在项目仓库中，可以开始处理”的说法

收到这类通知后，必须自动开始以下工作，不要只回答“收到”，也不要让用户再次说明分析步骤：

1. **读取项目规范**：读取本文件、项目 README 和 ITERATION_LOG.md，确认当前项目边界、版本主线和最近一次迭代状态。
2. **定位报告**：检查 `eslaulau/fm-ta` 当前默认分支的仓库目录/文件树，优先检查 `season-reports/` 及其下的赛季报告目录；同时检查用户在通知中明确指出的路径。不得凭文件名猜测报告内容。
3. **确定报告范围**：
   - 若用户指定了报告目录、文件名、日期或 run 编号，严格以该目标为准。
   - 若用户只说“报告在仓库”，列出并检查相关报告目录，识别新提交的报告及其内容；结合提交/目录信息判断最新报告。
   - 若存在多个同样合理、无法判断用户要分析哪一份的报告，先简短列出候选并只问一个必要的澄清问题，不得擅自挑选。
   - 不把 Actions 构建产物、战术 JSON 或旧报告误认成最新赛季报告。
4. **读取报告原始内容**：打开目标报告中的实际数据文件，读取所有与本规范分析范围有关的文件/表格；不能只看 README、文件名、摘要或旧聊天摘要。若报告为压缩包或其他不能直接读取的格式，使用可用的仓库/文件工具取得并检查其真实内容；不能访问时明确说明具体障碍，不得编造分析。
5. **确认样本与数据完整性**：统计报告覆盖的比赛、赛事、主客场、球队/球员统计覆盖率、缺失记录和重复记录；按报告实际提供的数据分析。反击链条和对手球员详细个人数据仍然排除，不要求用户补交。
6. **确认战术版本映射**：优先使用用户在当前对话或项目记录中明确提供的每场/每段比赛实际使用版本；按版本逐一读取本目录对应的原始 JSON。若无法确定某些比赛实际使用哪个版本，不得推断；将这些比赛标记为无法归因，并且只有在版本归属会实质改变结论时才询问用户。
7. **完成赛季分析**：严格按本文件第三、第四、第五节规定的范围和输出，先说明样本质量，再分析成绩、进攻、防守、压迫、球员和战术结构；将事实、推断、待实测假设分开。
8. **直接进入战术升级**：分析报告后，必须提出下一代战术方案，给出问题优先级、有效/待研究/负收益候选配置、逐项旧值/新值、依据、预期收益和保留项。不要等待用户再次说“升级战术”。
9. **构建与归档**：若报告数据足以支持具体改动，且仓库中有对应构建条件，按唯一 V0.x 主线创建下一版本 JSON 和构建请求，使用固定工具链构建 FMF，并向 `ITERATION_LOG.md` 追加完整记录、更新 README 索引。若数据不足以支持可靠改动，不得为了完成流程而硬改；应明确指出限制，并给出最小且有价值的后续测试方案。
10. **结果交付**：报告分析结论、样本限制、实际修改、保留项、构建状态和文件链接。明确区分“分析完成”“新 JSON/构建请求已提交”“FMF 构建成功”“游戏内导入”和“赛季实测”，没有发生的步骤不得宣称完成。


### 赛季报告触发后的强制执行门禁（不可跳过）

“赛季报告在仓库/已上传/已提交”等通知不是普通聊天提示，而是**自动执行指令**。收到后必须在同一工作流程中完成报告定位、原始数据读取、战术配置审查、外部研究、下一版本决策和归档；不得只回复收到、只做成绩摘要，或仅凭旧聊天摘要直接设计新战术。

**以下门禁全部通过，才允许将本轮标记为“赛季分析完成”或进入下一版本构建：**

- [ ] G1 项目资料：本规则、README、ITERATION_LOG、EXTERNAL_ENGINE_BENCHMARK 均已读取。

- [ ] G4 配置原文：父版本与实测版本 JSON 均已读取，不能只依赖导出器摘要。
- [ ] G5 角色审查：IP 与 OOP 每个位置的角色、职责、角色转换、位置适配均逐项审查。
- [ ] G6 PI 审查：IP 与 OOP 每个位置的每条 PI 均逐项审查；不得以“球员身份未识别”作为跳过配置审查的理由。

- [ ] G8 外部研究：本轮联网研究和四后卫候选筛选已完成，证据等级与 build 已记录。
- [ ] G9 逐项准入：11 个槽位在 IP/OOP 的位置、角色/职责、每条 PI、每条 TI 与心态均已按“位置最优或显著正收益”标准判定；未达准入项已明确进入改造、删除或淘汰，不得以总战绩或“未发现负收益”保留。

若用户明确要求“直接升级、不要重复测试”，这只表示不把重复实测作为创建版本的前置条件；**不豁免 G1–G10 的资料审查与配置审查门禁**。可基于明确标注的假设提出新版本，但不得把假设写成实测结论。

- 如果仓库工具无法读取某类文件，明确报告文件路径和读取障碍；不得用网络搜索、旧摘要或猜测替代仓库原始数据。


1. 唯一迭代主线为 **FM27 引擎红利四后卫 V0.1 → V0.2 → V0.3……**，不得擅自引入其他战术项目的实验结果或配置。

   - 战术生成器：[fm-ta](https://github.com/eslaulau/fm-ta)

   未经用户明确要求，不更换工具链。
4. 项目判断以 FM27 原版比赛引擎的实际数据为准，不以现实足球理论替代游戏实测。
5. 区分报告直接提供的数据、合理推断和待实测假设；不得把推测写成已证实的因果关系。

## 三、赛季数据分析范围

按导出器实际提供且有助于战术升级的数据分析：

1. **样本质量**：统计覆盖率、缺失记录、比赛数量、赛事分类、主客场分布。
2. **赛季成绩**：胜平负、进球、失球、积分、主客场及赛事分类。
3. **进攻表现**：xG、NPxG、射门、射正、绝佳机会、xA、关键传球。
4. **进攻推进**：控球、传球、推进、过人、传中、越位。
5. **防守表现**：对手 xG/xGA、对手射门、射正、绝佳机会，以及我方抢断、拦截、解围、封堵。
6. **压迫表现**：压迫次数、成功率、夺回球权；仅在报告确实提供时分析。
7. **球员表现**：出场时间、评分、进球、xG、助攻、xA、传球、过人及防守数据；尽可能计算每90分钟数据。
8. **失误与球权风险**：失误、丢失球权等与比赛表现直接相关的数据。犯规、黄牌、红牌不属于分析或验证指标。
9. **战术配置**：读取对应版本 JSON，核对 IP/OOP 位置、角色、职责、PI、TI 和心态。
10. **版本归因**：结合用户明确提供的实际使用版本与比赛范围，对照配置和赛季表现。

### 明确排除项
- 不分析、不要求导出反击链条。
- 不分析、不要求导出对手球员详细个人数据。
- 对手球队层面的统计（例如对手 xG、射门、绝佳机会）仍属于分析范围。
- 不擅自扩大导出范围；数据未提供时标记缺失，不将其列为用户必须补交的项目。

## 四、分析必须导向战术升级

**赛季数据分析不能以评价报告结束。最终必须进入战术升级环节。**

每轮分析必须回答：
1. 当前版本有哪些值得保留的引擎优势？
2. 哪些配置可能限制表现或产生负收益？
3. 最影响成绩的三个问题是什么？证据强度如何？
4. 下一版本具体改哪些配置？哪些配置必须保留？

根据数据，可以研究和调整以下方面：

- **阵型与结构**：IP/OOP 站位、位置、攻防转换位置、左右侧结构。
- **角色与职责**：球员角色、职责、位置适配、角色之间的组合。
- **球员个人指令 PI**：盘带、传球、射门、跑位、压迫、抢断等可编辑指令。
- **球队指令 TI**：节奏、宽度、传球方式、推进方式、射门、传中、防线、压迫、逼抢陷阱等。
- **进攻效率**：机会创造、射门质量、禁区威胁、传中收益、越位风险。
- **防守效率**：对手机会质量、射门限制、压迫与防守行为。
- **人员协同**：前场组合、左右侧分工、角色互补、IP/OOP 角色转换。
- **比赛风险**：失误、丢失球权、抢断方式、压迫频率和传球风险；不以犯规、黄牌或红牌评价配置效果。

**纪律数据排除规则：** 后续赛季分析不需要统计、分析或验证犯规、黄牌、红牌，也不得将其作为战术优劣判断、版本对照、PI/TI 调整依据或后续测试目标。历史报告中若出现这些字段，可忽略，不要求补交。此规则不妨碍读取和修改 TACKLING 等战术配置，但其效果必须用防守质量、机会限制等非纪律指标评估。\n\n数据现象只能用于提出诊断方向，不能单凭一个指标就认定某个 PI/TI 是原因。必须结合样本质量、球员位置、角色职责、完整战术配置及其他相关指标判断。


### 逐位置最优 / 显著正收益准入规则（最高优先级）

**总原则：战绩不错不构成任何位置、角色、职责、PI 或 TI 的保留理由。** 每个 IP/OOP 槽位、每个角色/职责、每条显式 PI、每条显式 TI，以及心态和可迭代站位字段，都必须单独通过以下至少一项准入条件，才允许作为“有效配置”保留：

1. **位置最优**：在相同 FM27 build、相同测试协议和可比阵容/对手条件下，该位置/阶段的配置在合理候选中达到最优或稳定处于最优档；必须有位置级或角色级证据，不能只引用整队排名。
2. **显著正收益**：不一定是所有候选中的第一名，但能通过受控对照、重复样本或多个独立可信来源，证明该配置在其对应位置/职责或整体战术中产生明确、可重复且超过样本噪声的净收益；同时评估其副作用与队友协同成本。

#### 判定纪律

- **逐位置**：11 个槽位的有球位置和无球位置分别审查。每个位置的站位、角色、职责及 IP↔OOP 转换必须有独立结论；不能用“全队踢得好”替代某个位置的优劣判断。
- **逐指令**：每条 PI 和 TI 分别判断。必须写清其适用位置/阶段、影响对象、收益指标、代价指标及证据来源；不能因为整队 xG、积分或胜率不错，就认定其中每一条指令都有效。
- **证据强度**：优先同 build 受控 A/B；其次为重复的大样本独立测试；单赛季总成绩、目录可编辑、角色位置资格通过、单一社区观点或未控制阵容的排行榜，都不能单独满足准入。
- **位置级指标**：尽量使用能可靠映射到实际槽位/角色的表现数据，例如该位置的机会创造/终结、推进、失位、对手针对区域的机会质量、关键防守动作等。位置或 role_code 未经验证时，必须标记“无法归因”，不得将球员汇总数据伪装成该位置证据。
- **净收益**：不能只看单一正向指标；同时审查负面副作用、相邻位置的损失、IP/OOP 转换代价及与其他 PI/TI 的交互。
- **不得以“没有证据证明它差”作为“证明它好”**。目录权限通过、原生编码合法、结构完整，只是技术可用性，不等于位置最优或实战正收益。

#### 强制决策标签

| 标签 | 含义 | 处置 |
|---|---|---|
| **准入保留** | 已证明位置最优，或有显著、可重复的正净收益 | 才能进入有效配置库 |
| **改造筛选** | 位置适配一般、非最优、冲突明显，或缺乏足够证据 | 必须进入候选替换/对照筛选；不得作为有效项原样保留 |
| **删除 / 淘汰** | 有负收益、明显冗余、位置职责不适配或被更优方案稳定击败 | 从下一版本方案中移除 |
| **证据不足（未准入）** | 当前数据无法判断位置收益或指令贡献 | 不等于保留；必须进入改造筛选或删除/淘汰队列，明确下一步替代候选，不得无限期沿用并称为有效配置 |
| **原生锁定** | 用户明确锁定的原生风格字段 | 仅保持原字节，不参与上述优化改写 |

#### 对照实验要求

- 候选比较必须尽可能固定 build、阵容、对手强度、赛程、主客场和测试协议；记录样本量与不确定性。
- 角色/职责应比较同一槽位的合理候选；PI 应比较该 PI 的不同状态及其与角色/TI 的交互；TI 应验证其整体净收益以及对关键位置的影响。
- 可一次研究相关配置组合，但必须能说明每个被保留字段自身的机制贡献；不得只凭一个组合整体成功就把组合内全部字段一并判为最优。
- 数据不足时不要求凭空删除所有配置，但当前版本只能作为可复现的**待筛选原始基准**；不能声称其位置/指令已被验证有效。下一版本必须提出具体替换/对照候选，未通过准入的字段不能列入“保留清单”。

### 角色与个人指令专项审查（每轮强制，独立于球队 TI 分析）

**角色/职责/PI 必须作为独立分析维度完成，不能被球队 TI 分析替代。** 每轮必须对父版本和本轮实测版本的完整 JSON 逐项审查，并按“位置最优或显著正收益”准入规则作出决定；仅完成配置审查不代表该配置通过效能准入。

#### A. 逐位置角色审查
- 分别列出 IP 与 OOP 的全部位置槽位；逐个核对角色、职责、位置、IP↔OOP 转换关系。
- 对每个位置判断：角色职责是否适配该位置；角色是否与相邻位置形成互补或重复；是否造成无人提供宽度/保护/推进/禁区攻击/回防；是否出现同侧拥挤、中央堆叠或防守通道暴露。
- 必须单独检查无球最后防线人数与真实四后卫结构；不得只根据阵型标题推断。
- 对角色权限、可用 PI 和角色职责限制，必须以当前项目 catalog/生成器定义核验；不允许凭角色名称猜测可用性。

#### B. 逐条 PI 审查
对 IP/OOP 每个位置下的每一条显式 PI，逐条记录：
1. 位置、阶段、角色/职责、PI 字段、当前值；
2. 该 PI 对球员行为的预期影响（机制解释，标明证据等级）；
3. 是否符合该角色职责和球员所在位置；
4. 是否与同位置其他 PI、队友角色/PI、球队 TI 或攻防转换职责冲突/重复；
5. 可能收益、可能副作用、可观测的非纪律指标；
6. 结论：准入保留 / 改造筛选 / 删除或淘汰 / 证据不足（未准入）/ 原生锁定；
7. 若建议修改，列出旧值→新值、证据来源、预期收益和风险。

未显式写入的 PI 也要检查是否依赖游戏默认值；若默认值无法从 catalog/引擎定义确认，标注“默认行为未核实”，不得擅自认定其具体效果。PI 列表为空的位置也必须明确记录“无显式 PI”，不能遗漏该位置。

#### C. 组合与冲突审查
至少覆盖以下组合关系：
- 左右边路宽度、套边/内收、边锋/边后卫/中卫重叠；
- 双中卫与后腰的出球分工、保护区域和压迫触发；
- 前场球员的盘带、跑位、自由移动、前插、禁区攻击点是否重复或互相挤占；
- False Nine/支点/攻击线角色与第二前锋、攻击型中场的纵深和接应关系；
- PI 的传球长度/风险与 TI 的传球方式/节奏/空当指令；
- PI 的压迫、盯人、抢断与 OOP 角色、团队压迫线、防线高度和压迫触发；
- IP/OOP 转换后是否出现职责断层、同一球员两阶段任务互相抵消。

#### D. 球员赛季数据与角色归因
- 只有当球员逐场身份、实际上场位置/槽位、使用版本和比赛记录可以可靠对应时，才允许把表现归因到某个角色或 PI。
- 如果球员身份、位置或逐场角色映射缺失：必须完成 A–C 的配置层审查；球员数据只能作全队/球员汇总描述，不得伪造角色表现，也不得因此跳过角色/PI 分析。
- 对可映射球员，优先计算每90分钟及首发/替补差异；明确样本量和出场分钟，避免用赛季总量直接判断 PI 效果。

#### E. 强制交付格式
每轮必须输出并归档以下四张表/清单：
1. **IP/OOP 角色矩阵**：所有位置、角色、职责、转换、适配判断；
2. **PI 逐条审查表**：不得只抽查“看起来有问题”的 PI；必须覆盖 JSON 中全部显式 PI；
3. **角色/PI 组合冲突表**：左右侧、前场、中后场、PI↔TI 交互；
4. **逐项准入与处置表**：每项标记准入保留/改造筛选/删除或淘汰/证据不足（未准入）/原生锁定，并列出证据、替代候选和理由。

角色/PI 审查完成后，才可形成下一版本的 TI 调整方案。允许最终只改 TI，但必须证明角色和 PI 已经审查且本轮保留它们的理由；也允许优先改角色/PI。不得预设每轮必须修改多少项，更不得为了完成表格而无依据地乱改；但凡未达到准入标准的配置，必须进入改造筛选或删除/淘汰流程，不能继续以“保留”名义原样通过。

## 五、每轮升级方案的强制输出

分析完成后，必须提出明确的下一版本方案，至少包含：

1. **问题排序**：最影响表现的三个问题及数据依据。
2. **配置分类**：
   - **准入保留配置**：逐位置/逐指令证明最优或显著正净收益，方可保留。
   - **改造筛选配置**：位置非最优、协同冲突或证据不足；必须列出替代候选和处置路径，不能把“待研究”当成保留。
   - **删除/淘汰配置**：已证实负收益、冗余或不适配，明确从下一版本移除。
3. **变更清单**：逐项列出配置字段、所在 IP/OOP 或 TI、旧值、新值、修改依据和预期收益。
4. **准入保留清单**：只列已达到“位置最优或显著正收益”门槛的项目；仅未发现负收益、配置合法或没有数据归因的项目不得列入。
5. **实验控制**：优先小范围修改少量变量，确保新旧版本可比较；只有证据指向结构性问题时才进行较大调整。
6. **版本定义**：按 V0.x 顺序递增，明确父版本，不覆盖历史版本。

如果数据不足以支持具体改动，仍须给出证据边界和最有价值的下一步测试方案；不得为了“升级”而随意改动配置。

4. 按需更新本目录 README 中的版本索引和链接。

## 七、新旧版本实测对照

- 样本范围不一致时，使用共同比赛范围或合理的每场/每90分钟指标；不得直接比较不等量总数。
- 对比进攻、防守、压迫、球员收益及比赛结果；不统计或比较犯规、黄牌、红牌。
- 判断每项改动是保留、回退还是继续研究。
- 将实测结论追加到对应版本的 `ITERATION_LOG.md`。

## 八、标准工作流程

收到赛季报告入库通知 → 读取规则/README/迭代日志 → 定位并读取仓库中的原始报告 → 检查样本质量 → 按用户说明确认实际战术版本并读取对应 JSON → 完成赛季分析 → 自动制定下一版本升级方案 → 数据充分时创建新 JSON/构建请求并生成 FMF → 追加迭代日志并更新 README → 下一轮用同口径数据对照。

## 九、外部引擎研究与战术榜单交叉基准（新增强制规则）

**外部研究是本项目正式研发输入。** 每次分析赛季报告、设计下一版本、评估引擎红利或提出配置变更前，必须进行联网检索；不能只围绕本项目旧报告和旧战术闭门迭代。

### 9.1 必查资料类别
按当前 FM27 游戏版本/比赛引擎 build 搜集并记录：
1. **机制与引擎研究**：社区对角色、职责、PI、TI、站位、攻防转换、压迫、防线、传中、跑位、射门等机制的实测、拆解和复现实验。
2. **大样本战术排行榜**：优先查找有统一测试协议、样本量、对手强度分组、误差范围或置信区间的排行榜。
3. **社区战术测试库**：收集不同网站的实测结果、战术文件、测试场景、样本量和版本号。
4. **战术结构分析工具**：用来解析候选战术的 IP/OOP 阵型、角色职责、球员指令、球队指令及结构冲突。
5. **社区讨论与复现实例**：论坛、作者说明、测试视频等可用于提出机制假设，但不能单独作为强证据。

### 9.2 来源分级与交叉验证
- **A级：受控大样本测试**。同一游戏 build、统一测试协议、相同球员/对手或明确控制强度，公布样本量及结果；如有误差范围必须记录。
- **B级：独立测试/跨站复现**。不同组织采用可说明的方法进行自动或人工测试，能核对版本、赛程、样本量和成绩。
- **C级：社区实测记录**。有比赛数量和结果，但球队、球员、赛程、操作方式等条件不统一。
- **D级：作者宣称、单场展示、视频观感或未提供原始数据的机制说法**。只作为待验证假设。
- 同一作者转载、同一数据源镜像或同一测试集的多个页面不算独立证据。
- 不得把不同游戏版本、不同 build、不同测试协议的 PPG、Pts/38、胜率或进球数据直接合并排名；必须分组标注。排行榜排名不能替代原始测试数据。
- 记录抓取日期、游戏版本/build、测试协议、样本量、对手/球队条件、指标定义、误差范围、原始链接及证据等级；注明页面动态变化和未能读取的内容。
- 外部数据与本项目赛季报告冲突时，不直接择一相信；检查阵容、球员能力、战术熟悉度、赛程、比赛操作、引擎 build 和统计口径，再设计可复现测试。

### 9.3 四后卫专项筛选（不可被榜单总排名带偏）
- 必须单独筛选**无球阶段真实四后卫**候选，并同时记录有球与无球阵型；不能只看战术标题或基础阵型。
- 以无球最后防线人数/结构为核心判定依据，区分真实四后卫、三中卫、五后卫及动态转换体系；不明确者标记“待核对”，不得混入四后卫排名。
- 三中卫/五后卫榜单冠军可以用于发现角色、PI、TI、跑位或引擎机制候选，但不能作为四后卫成绩基准，也不能直接照搬其结构。
- 在各网站内先按同一 build、同一协议、相近测试条件比较，再建立跨站的证据矩阵；不制作虚假的统一总榜。
- 优先保存可下载的原始 FMF，解析其真实 IP/OOP 站位、角色、职责、PI、TI，与本项目 V0.x JSON 对照。只看网页战术名称/阵型描述不算完成配置分析。

### 9.4 引擎红利基准库与迭代方式
- 维护本目录的 [EXTERNAL_ENGINE_BENCHMARK.md](EXTERNAL_ENGINE_BENCHMARK.md)，作为外部来源、榜单快照、机制假设、候选战术配置和证据等级的持续档案。
- 每次外部研究追加日期化快照，不覆盖旧快照；榜单变化需保留旧值与新值。
- 将发现归入：已被多源支持的候选机制、单一来源候选、存在争议/反例、尚待本项目实测。
- 对每个候选记录具体字段/角色/位置、预期作用、适用结构、可能副作用、来源和复现实验方法。
- 研究结论必须映射到本项目四后卫可用位置/角色/PI/TI；不适配的配置明确排除，不为追榜单牺牲四后卫边界。
- 新版本优先做小变量 A/B 或分阶段实验。外部榜单提供候选和参照，本项目相同条件实测决定保留、回退或继续研究。
- 任何外部网站的战术排名都不得直接写成“引擎机制已证实”；机制主张必须有直接机制测试或多源独立复现。

### 9.5 每轮输出新增要求
