# FM27 引擎红利四后卫：正式研发与迭代规则

本文件是 FM27 引擎红利四后卫项目的正式执行规范，取代此前以“无球真实四后卫”“逐字段最优准入”和“单变量实验”为中心的旧流程。

## 一、研发目标与边界

### 核心目标

开发一套利用 FM27 当前比赛引擎机制、在有球阶段形成四后卫结构的高效战术。设计依据是引擎红利资料库、FM27 当前 build 的可核验研究、用户确认的战术赛季报告和原生 FMF 配置。

项目不以现实足球理论作为设计约束。现实足球中的阵型习惯、角色分工、位置职责和教练理念，不能否定游戏引擎数据支持的非传统组合。

### 有球四后卫定义

有球阶段的四个后场防守位置必须由 DL、DCL、DCR、DR 构成。可以按引擎需要调整四个位置的角色、职责、PI，以及其与门将、中场和前场球员的联动，但不得把研发目标偷换成三后卫或五后卫有球结构。

无球阶段不要求维持四后卫。OOP 阵型、角色、职责和转换位置可以独立优化；只要有助于整体引擎收益和有球四后卫战术发挥，就允许采用不同人数和不同结构。不得再把“无球最后防线必须是真实四后卫”作为设计约束或准入门槛。

### 四后卫角色与指令不锁定（强制澄清）

**“有球四后卫”只锁定四个后场位置槽位为 DL、DCL、DCR、DR，不锁定这四个槽位的任何具体角色、职责或个人指令。** 四名后卫的角色可以互换或采用不对称组合；职责可在防守/策应/进攻之间重设；PI 可按位置、角色、职责及原生权限重新设计。允许边后卫内收、中卫拉宽、翼卫前插、出球中卫承担推进等非传统组合。只要 IP 的四个后场位置仍为 DL–DCL–DCR–DR，就满足结构约束。OOP 的角色、职责、PI 与阵型转换完全开放，不得因历史版本相同而默认锁定。

### 项目边界

- 唯一迭代主线：V0.1 → V0.2 → V0.3 → ……；每版记录唯一父版本，历史版本不得覆盖。
- 外部战术不整套复制。外部资料用于识别引擎机制和候选组合，再结合本项目赛季数据重新设计。
- 只有用户明确提供的战术版本映射才可用于赛季归因；不得臆测每场实际使用的 tactic。
- 后续所有表现分析排除犯规、黄牌、红牌，不得用其作为战术优劣指标或配置调整依据。

## 二、每轮强制五步流程

### 1. 读取赛季报告

读取目标报告的原始文件，而不是只看摘要。核对比赛数量、赛事类别、主客场、球队统计覆盖、球员报告覆盖、缺失和重复记录、游戏 build、解析器兼容性与身份识别质量。

按胜场、平局、败场分组，分析比分、进球、失球、xG、NPxG、射门、射正、绝佳机会、控球、推进、传球、传中、防守质量及球员表现。区分联赛、杯赛、洲际赛事；不同赛事和不同样本量不得混合解释。

球员指标尽量按分钟和每90分钟分析。只有球员身份、位置语义、逐场战术槽位和版本映射均可信时，才允许把个人数据归因到某个角色或 PI。位置码未验证或 role_code 未解码时，照常完成球员表现分析，但不得伪造位置/角色归因。

### 2. 找出战术优势与弱点

从整体战术找出优势和问题，至少覆盖：

- 进攻：机会创造、禁区威胁、终结、射门质量和得分转化；
- 推进：从后场到中场、从中场到前场的连接，传球、持球和进入前场三区的能力；
- 防守：对手射门、射正、绝佳机会、xG 与推进威胁；
- 转换：得球后的推进与丢球后的防守恢复；
- 位置与协同：有球四后卫、双中场、前腰、边路和前锋之间的空间分布、接应、跑位、职责重叠或断层；
- 球员表现：产量、效率、评分和可识别的稳定贡献。

优先分析胜、平、负差异，以及主场/客场差异。单项统计相关性不是因果证明；不得仅凭一个数字判定某项角色或指令是失败原因。

### 3. 重新设计整套配置

根据问题重构战术，不受每轮修改数量限制。可以同时调整：

- IP / OOP 阵型位置与转换；
- 角色和职责；
- 每个位置的 PI；
- 球队 TI；
- 心态及其他已核实的原生战术配置。

允许多个相关改动协同完成一个整体设计。不得为了满足“单变量”而保留已发现的结构冲突；也不得把“尚未单独证明某项 PI”理解为不能调整。

每项改动须说明当前问题、具体旧值→新值、与其他配置的协同关系、数据依据、引擎机制依据、预期收益和主要风险。明确区分报告观察、合理推断、外部资料支持和本轮设计假设。

证据不足时，可以保留为暂定配置，也可以按整体设计调整；不能把未知写成已验证，也不能仅因为未知就冻结全部配置或自动删除。单变量 A/B 或专项测试只在确实需要澄清关键因果问题时作为辅助工具，不再是正常战术升级的目的或前置门槛。

### 4. 生成下一正式版本 FMF

每轮按唯一父版本构建新的 FMF，不覆盖历史版本。必须核验：

- 父版本文件 SHA-256 与父子版本关系；
- 有球四后卫的四个位置确实为 DL、DCL、DCR、DR；
- 11 个槽位的 IP/OOP 位置、角色、职责和转换关系；
- 新角色的原生位置资格与 duty 兼容性；
- 新增/修改 PI 的阶段、位置、角色、职责权限；
- TI 原生 bit 向量与写入后读回值；
- 原生 style string、FourCC、TAC footer、ID lists、AOM、IMG 和其他 opaque 成员的保护情况；
- FMF 再解析与 read-after-write。

只有实际执行并通过的检查才能标记 PASS。原生文件回读不等于游戏内导入；游戏内导入不等于赛季实测。

### 5. 正常赛季复盘

新版本进入正常赛季使用后，按同样口径重新读取报告，比较新旧版本在相近赛事范围、主客场和样本中的整体表现。重点看胜平负、积分、进球/失球、xG/xGA、机会质量、进攻推进、球员贡献和比赛稳定性。

不得因为某一个指标改善就宣称战术成功。必须同时检查代价、负面副作用和不同比赛情境的表现；继续从整套战术诊断并迭代下一个版本。

## 三、数据与证据纪律

### 数据质量

报告必须记录实际样本覆盖与兼容性风险。schema 布局借用、目标 build 未上游登记等情况应如实标记；若交叉核验和总量对账通过，可用于描述性分析，但不能宣称所有字段已获得上游语义认证。

### 证据类别

1. 报告直接观察：原始比赛、球员或配置文件中可复核的事实。
2. 关联现象：结果分组、主客场或球员表现存在的统计差异。
3. 机制依据：FM27 当前 build 的引擎研究、原生设置和外部可复核战术资料。
4. 设计假设：根据以上信息提出的 V0.x 配置方案，等待新版本正常赛季复盘。

不存在“每条 PI/TI 必须先独立达到位置最优或显著正收益才允许保留”的门槛。配置审查的目的是发现问题和设计解决方案，不是阻断整套战术升级。

### 外部资料

每轮结合当前 FM27 build 检索引擎更新、测试榜单、社区实测和原始 FMF。记录游戏 build、日期、样本量、测试协议和指标。不同网站、不同 build、不同对手/球员协议的数据不可直接混排。榜首战术可提供机制线索，但不能直接替代有球四后卫目标，也不能复制整套配置。

## 四、原生 FMF 保护规则

V0.7 的唯一父版本为 V0.6。其原生文件身份由 V0.6_BUILD_REPORT.json 中的 SHA-256 固定。

本主线唯一明确锁定的战术身份字段：
- 原生 style string 始终为空字符串；
- 原生 FourCC 始终保留为 4c4c554e；
- 不得为了使用官方风格模板而改成 Gegenpress、Control Possession 或其他命名风格；
- 必须以实际父版本 FMF 为容器和 TAC 原生数据来源，进行定点字段更新和二进制 read-after-write。

对未授权修改的字段及 opaque 数据应尽量原样保留。任何新增角色、职责、PI 或 TI 必须以当前仓库 catalog 和原生字段映射核验；未知编码不猜测。

## 五、自动触发与交付

用户明确说出赛季报告已在仓库、已上传或可以分析时，自动开始本规范五步流程，不得只回复收到或要求用户重复目标。若报告路径或版本归属仍无法确定，并且会实质改变结论，才询问最少的一个必要问题。

每轮交付至少包括：报告分析、优势与弱点、战术设计决策、V0.x 配方、原生 FMF 与构建报告、构建/回读状态，以及尚未完成的游戏导入或赛季实测状态。
