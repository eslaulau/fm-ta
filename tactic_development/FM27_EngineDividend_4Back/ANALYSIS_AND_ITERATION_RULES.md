# FM27 引擎红利四后卫：正式研发与迭代规则

本文件是本项目的正式执行规范。它覆盖整套赛季数据分析、战术设计、原生构建、游戏内验证和比赛效果迭代；生成器 D3 只是其中一个技术阶段。

## 一、研发目标与边界

开发一套利用 FM27 当前比赛引擎机制、在有球阶段形成四后卫结构的高效战术。设计依据包括当前 build 可复核的引擎机制研究、外部大样本与榜单资料、用户确认的完整赛季报告、原生 FMF 配置及实际游戏内验证。

项目不以现实足球理论作为设计约束。现实足球中的阵型习惯、角色分工、位置职责和教练理念，不能否定游戏引擎数据支持的非传统组合。

### 有球四后卫定义

有球阶段四个后场防守位置必须由 DL、DCL、DCR、DR 构成。这是唯一战术结构硬约束。四个位置的角色、职责、PI 均可调整，也可以采用内收边后卫、中卫外扩、翼卫前插、出球中卫推进等非传统组合。

无球阶段不要求维持四后卫。OOP 阵型、角色、职责和转换位置可以独立优化；只要有助于整体引擎收益和有球四后卫战术发挥，就允许采用不同人数和不同结构。

### 四后卫角色与指令不锁定

有球四后卫只锁定四个后场位置槽位为 DL、DCL、DCR、DR，不锁定任何具体角色、职责或 PI。OOP 的角色、职责、PI 与阵型转换完全开放，不得因历史版本相同而默认锁定。

### 项目边界与研究假设

- 唯一版本主线按父子关系递进，每版记录唯一父版本及 SHA-256；历史版本和构建产物不得覆盖。
- 外部战术用于识别引擎机制和候选组合，不整套复制；最终配置由本项目数据、机制与原生权限重新设计。
- 只有用户明确确认的战术版本映射才可用于赛季归因；不得臆测每场实际使用的 tactic。
- 用户提出或外部研究发现的候选机制均应标注为待验证假设，而非固定教条。例如不同位置分化的触发逼抢、广泛或分层使用积极铲抢等，都应结合当前 build、角色权限和整体结构重新评估。
- 用户研究中的积极铲抢假设不得因出现于多个位置就自动视为无意义填充；也不得使用犯规、黄牌、红牌来判断其战术价值。应优先查看可用的抢断成功、对抗结果、球权恢复、对手推进、射门质量和 xGA 等非纪律指标。
- 所有战术表现分析排除犯规、黄牌、红牌，不得将其作为战术优劣指标或配置调整依据。

### 已有“引擎红利”研究线索（保留为待验证假设）

以下是本项目已由用户提出并要求延续的研究方向。它们是战术研发的候选机制池，不是已证明的普遍规律；每轮需注明 FM27 build、样本协议、适用位置/阶段和本队赛季证据，不得直接套成固定配置。

1. **IP/OOP 双阵型切换：** 用户整理的 FM-Arena/FMAX 大样本研究线索（用户记录的累计样本超过 38.5 万场）提示，META 常见模式是有球与无球采用不同结构；部分高效方案无球阶段采用无锋或前场不设传统中锋的结构，并以纵深跑动攻击空间。该样本总量、排名和测试协议必须在外部基准文件中逐次留存快照，未核对具体原始页面前不把“38.5 万场”当作本仓库独立验证结果。
2. **无球无锋纵深：** 将 OOP 前场压迫人数与纵深跑动分开研究。无锋并不等于缺少前场威胁；需要检查断球后前场接应、攻击纵深、反击传球、跑位时机和对手出球压力。
3. **防线与压迫组合：** 较低防线搭配较高压迫/积极逼抢是既有候选组合；更新后的 build 中，较高防线搭配较积极压迫也可能成立。不得把团队压迫频率推到最高档作为默认方案，应根据对手出球、后场空间、xGA 和球员属性评估档位。
4. **个人压迫频率分化：** “更多地逼抢（Trigger Press More Often）”优先作为边后卫/翼卫、中卫以外的中路防守者、双后腰及前场三人组的候选；“较少地逼抢（Trigger Press Less Often）”可作为中卫保护先进边后卫身后空间的候选。必须按 IP/OOP 阶段、实际位置、角色和职责分别审查，不把同一设置机械复制到所有阶段。
5. **积极铲抢：** “更凶狠地铲球（Tackle Harder）”可以作为广泛使用的引擎候选，而不是因多位置使用就自动判定为无意义 PI。用户此前将 27.1.0 对抗/牌数变化作为该假设的背景线索；本项目的效果评估仍不得使用犯规、黄牌、红牌，改看抢断成功、球权恢复、对抗结果、对手推进、射门质量与 xGA。
6. **其他防守指令：** 对手指令（OI）避免过度堆叠；只在对手特征与当前防守结构有明确对应关系时选择，不把 OI 数量当作压迫强度或战术质量的代理指标。
7. **属性与角色权重：** 角色、职责与 PI 的收益受球员属性、位置上下文、对手计划和 IP/OOP 结构影响。外部大样本的 META 不等同于本队球员条件下的最优解，必须通过本队赛季数据复盘。

## 二、每轮强制五步流程

### 1. 读取赛季报告与确认数据口径

读取目标报告的原始文件，而不是只看摘要。核对比赛数量、赛事类别、主客场、球队统计覆盖、球员报告覆盖、缺失和重复记录、游戏 build、解析器兼容性与身份识别质量。明确用户确认的战术版本映射。

按胜场、平局、败场分组，并区分联赛、杯赛、洲际赛事；不同赛事和样本量不得混合解释。球队整体指标、球员指标、位置/角色数据的可信度要分别标注，不能因整体覆盖完整而假设每个角色都已完整识别。

球员指标尽量按分钟和每90分钟分析。只有球员身份、位置语义、逐场战术槽位和版本映射均可信时，才允许把个人数据归因到某个角色或 PI。位置码未验证或 role_code 未解码时，仍完成球员产量分析，但不得伪造位置/角色归因。

### 2. 找出战术优势与弱点

至少覆盖以下方面：

- 进攻：机会创造、禁区威胁、终结、射门质量、xG/NPxG 和实际得分转化。若数据源提供 NPxG 或点球拆分，应明确采用哪一种口径。
- 推进：后场到中场、中场到前场的连接，传球、持球、推进传球和进入前场三区能力。
- 防守机会控制：对手射门、射正、绝佳机会、xG/xGA 与推进威胁。
- 结果转化：实际失球与对手 xGA 的差额、实际进球与我方 xG/NPxG 的差额。将机会控制与终结/门将结果分开描述；差额本身不能证明运气、门将或防守结构是唯一原因。
- 转换与协同：得球后的推进、丢球后的恢复、IP/OOP 结构切换；有球四后卫、双中场、前腰、边路和前锋之间的空间、接应、跑位、职责重叠或断层。
- 球员：产量、效率、评分、每90分钟和可识别的稳定贡献。

优先分析胜、平、负差异及主客场差异。对于前场三区传球等原始次数，必须尽可能按每90分钟、控球时间/控球率、总传球数、每100次总传球、对手强度和比赛比分状态归一化。缺少总传球或控球时间时，原始次数只能作为推进信号，不得单独据此断定推进效率下降。

必须分别判断对手获得了更多/更好的机会与对手实际进球高于其 xG。例如败场组对手 xGA 明显高于胜场组，代表机会控制本身恶化；实际失球又高于对手 xGA，则是另一层结果差额。不得把全部失球归因于运气，也不得仅凭实际失球就认定阵型结构完全失败。

不同版本从同一初始存档重新模拟，也不等于相同随机种子、同一比赛状态的受控重放。共同赛程比较只能作为描述性证据，不能宣称单项 PI/TI 的因果作用。只有有明确相同 seed/状态并保持其他条件的受控实验，才可以提高因果解释力度。

### 2.1 诊断必须沿“结果 → 机会 → 战术过程 → 配置”逐层下钻（强制）

不得从比分或积分直接跳到某个角色/PI/TI 的结论。每轮按以下层级寻找问题来源：

1. **比赛结果层：** 胜平负、积分/PPG、进失球、净胜球；同时看主客场与赛事口径。
2. **机会质量层：** 我方 xG/NPxG、对手 xG/xGA、绝佳机会、射门质量和禁区威胁。区分“创造机会不足”“机会质量差”“对手获得高质量机会”和“结果转化偏离预期”。
3. **战术过程层：** 后场出球、推进、进入进攻三区、禁区进入、边中路供给、反击、丢球后恢复、压迫和防守空间保护。只能使用报告实际提供且语义可靠的指标；没有数据就标记未观测，不得用主观描述补成事实。
4. **配置层：** 再判断问题更可能来自 IP/OOP 结构、位置转换、角色/职责、PI/TI 协同，还是球员执行与阵容条件。只有配置身份、逐场槽位和数据覆盖可信时，才继续下钻到具体位置或单条指令。

必须把以下情况分开处理：
- 进球少但 xG/绝佳机会正常：优先检查终结、球员状态和机会转化，不得自动重做进攻阵型。
- 进球多但 xG/机会质量偏低：不能把短期高转化当成稳定战术优势。
- 失球多且 xGA/对手绝佳机会同步恶化：这是机会控制问题，不能简单归因于门将或运气。
- 失球高于 xGA、但对手机会质量没有同步恶化：将其记为结果转化差额，继续检查门将/个人执行等可用证据，不得直接认定防线结构失败。
- 控球、传球或推进次数增加：必须同时检查有效进入危险区域和最终机会质量，不能把活动量增加等同于进攻效率提高。

样本分组至少考虑胜/平/负、主/客场；报告允许时再检查领先/平局/落后时段、对手强弱和不同赛事。每个分组都必须显示样本数；小样本只作提示，不做稳定规律。不得为了凑齐分组而把数据不足的比赛强行归类。

### 2.2 每轮必须给问题定级，而不是罗列统计（强制）

将发现的问题分为：
- **结构级：** IP/OOP 阵型、位置转换、球队整体宽度/纵深、前场出口数量、后场保护、攻防转换结构。
- **协同级：** 相邻位置角色职责冲突、同一区域重复占位、通道无人占据、推进与接应断层、压迫与保护不匹配。
- **指令级：** 单个角色/职责、PI、TI 或 OI 的具体设置。
- **执行级：** 球员属性/熟练度/状态/分钟、伤停轮换、个人决策或数据覆盖问题。

每个重要问题必须写明：出现频率、影响范围、对应指标、证据可信度、可能的非战术解释，以及它属于上述哪一级。按“重复程度 × 对比赛结果/机会质量的影响 × 证据可信度”排序，先处理高影响且证据较可靠的问题；不得因某项统计显眼就自动把它列为首要升级目标。

每轮最终形成一份**问题优先级清单**，明确哪些是本轮要解决的主问题、哪些只是监测项、哪些因数据不足暂不判断。不能把所有异常统计都转化成战术改动。

### 3. 重新设计整套配置

根据整体问题重构战术，不受每轮修改数量限制。可以同时调整 IP/OOP 阵型位置与转换、角色和职责、每个位置的 PI、球队 TI、心态及其他已核实的原生战术配置。

**心态可变规则（强制）：** 心态是可自由优化的战术变量，不是项目硬约束。每轮都必须根据赛季诊断、引擎机制和整体战术目标重新评估；有依据时可以改变，不得因为父版本心态值、保持继承或单变量实验习惯而锁定。心态若改变，必须纳入完整父子差异及四类决策台账；若保持不变，也必须是有意的设计/证据决定，而不是规则强制。项目唯一不可违反的结构约束是有球阶段后场四个位置为 DL、DCL、DCR、DR；心态不属于该结构约束。

允许多个相关改动协同完成一个整体设计。不得为了满足单变量而保留已发现的结构冲突；也不得把尚未单独证明某项 PI 理解为不能调整。

每项重要改动说明：当前问题、旧值→新值、与其他配置的协同关系、数据依据、机制依据、预期收益和主要风险。明确区分报告观察、关联现象、外部资料支持、机制推断和本轮设计假设。

证据不足时，可以保留为暂定配置，也可以按整体设计调整；不能把未知写成已验证，也不能仅因为未知就冻结全部配置或自动删除。单变量 A/B 或专项测试只在需要澄清关键因果问题时作为辅助工具，不是正常战术升级的目的或前置门槛。

### 3.1 战术搜索广度与设计深度（强制）

本项目的研发目标不是把某一个历史阵型不断微调到看似合理，而是在唯一结构约束下，持续搜索更有引擎收益的整套战术架构。**不得默认当前正式版本、历史最高分版本或最近一次成功版本就是搜索空间的中心或上限。**

#### A. 搜索空间边界

- 唯一固定条件：IP 后场四个位置槽位必须为 DL、DCL、DCR、DR。
- 除这四个位置槽位外，其余位置分配、IP 阵型形态、角色、职责、PI、TI、OOP 阵型和 IP↔OOP 转换均可重新设计。
- 不得把“4-2-3-1”“双后腰”“单前锋”或任何历史常用结构视为默认起点、必备骨架或不可替换条件。
- 可以探索对称或非对称结构、不同中场层数、不同前场人数和高度、不同边路/肋部占位，也可以采用现实足球中少见但原生引擎允许的角色职责组合。
- 阵型名称不能代表完整战术结构。必须检查实际 11 个槽位的位置、角色、职责、跑动和 IP/OOP 转换；同一阵型名称可以有完全不同的引擎行为，不同阵型名称也可能形成相近的空间结构。

#### B. 每轮必须做一次结构搜索审查

在决定沿用当前结构或进入局部调整前，必须回答：
1. 当前主要问题是否可能由现有 IP/OOP 架构本身造成，而不是某条 PI/TI 设置造成？
2. 是否存在另一类满足 IP 四后场约束、但能更直接解决本轮问题的结构？
3. 当前结构的前场出口、纵深跑动、宽度、肋部占位、中场连接、后场保护和攻防转换，是否存在由人数/位置分配造成的先天限制？
4. 本轮选择继续当前架构、局部重构或整体重构的证据和理由分别是什么？
5. 哪些不同结构家族尚未充分探索，不能因为未测试就写成无效？

如果本轮只做局部调整，必须明确说明为什么结构级问题不是当前主要瓶颈，或者为什么现有数据不足以支持结构替换。不能仅以“上一版成绩不错”“改动较少”或“方便比较”为理由，自动沿用旧架构。

#### C. IP 与 OOP 必须作为可独立组合的搜索维度

- IP 搜索重点：在固定 DL/DCL/DCR/DR 四个后场槽位下，重新分配其余七个槽位，探索不同的中场人数/层次、前场人数/层次、边路宽度、肋部占位、禁区攻击人数和出球连接。
- OOP 搜索重点：独立研究第一压迫线、前场出口/回收人数、中场屏障、边路覆盖、后场防线人数与保护层次；不要求 OOP 继续保持四后卫，也不要求与 IP 保持同名阵型。
- 转换搜索重点：检查各槽位在 IP 与 OOP 之间如何移动，转换后是否形成额外后场保护、压迫人数、反击出口或纵深跑动；重点评价转换后的空间与职责，而不只看纸面阵型数字。
- 无锋、双前锋、三前场出口、单前锋、前场球员回撤到中场或中场球员前插等方案都属于可研究结构，不预先判定优劣。

#### D. 结构探索与局部优化要有明确优先级

- 若主要问题属于结构级，优先重构整体空间结构；不得用堆叠 PI/TI 代替阵型和位置分配调整。
- 若主要问题属于协同级，优先调整相邻位置关系、角色职责或 IP/OOP 转换；不要把协同问题误判为单项 PI 问题。
- 若主要问题确属指令级，才优先局部调整 PI/TI/OI；不为追求结构新颖而无理由推翻有效协同。
- 每轮可在设计阶段比较多个结构候选，但正式构建与赛季迭代仍按唯一父版本、一次推进一个正式候选执行；不要求并行生成多套 FMF。
- 对未充分探索的结构，记录为“未测试/未知”，不能记录为“无效”。对已测试但失败的结构，要说明失败的是具体配置组合，还是有足够证据否定更广泛的结构机制；一次失败不得自动否定整个阵型家族。

#### E. 结构搜索覆盖记录

每个正式版本的设计审计必须附一段简明的“结构搜索判断”，至少记录：
- 当前 IP 结构类型及 OOP 结构类型；
- 本轮是否延续、局部重构或整体重构；
- 本轮考虑过的其他结构方向，以及未选择它们的理由；
- 尚未充分探索的结构家族；
- 当前结构的主要引擎机制假设、预期收益和最大风险；
- D5 应检查哪些空间/转换指标来判断该结构假设是否成立。

这段记录写入现有版本设计审计和跨版本决策台账，不另建重复的流程或资料系统。记录结构搜索状态时，必须区分“已构建”“已游戏内导入”“已完成 D5”三个层次；只生成过 recipe/FMF 不代表该结构已完成实战测试。

### 3.2 结构决策门槛：沿用、局部重构还是整体重构（强制）

本节不重复3.1的搜索空间清单；3.1负责“有哪些结构值得搜索、搜索覆盖是否充分”，本节负责“根据本轮诊断选择哪种改动层级”。

每轮D0必须先引用2.1/2.2的问题诊断，再作出以下判断：
- **沿用当前结构：** 主要瓶颈不在结构级，或现有证据不足以支持结构替换；必须说明为什么当前结构仍能承载目标机制，以及本轮局部改动如何解决问题。
- **局部重构：** 问题集中在某条线、某侧、相邻位置关系或某一阶段转换；明确重构范围及其与未改部分的连接。
- **整体重构：** 问题由整体人数分配、空间层次、前场出口、后场保护或IP/OOP转换架构造成；必须优先调整阵型、位置分配或阶段转换，不得用堆叠PI/TI掩盖结构问题。

审查时须确认：本轮所选方案仍满足IP后场DL/DCL/DCR/DR硬约束；角色职责与原生权限可实现；结构改动不会未经说明地破坏已观察到的有效协同；D5指标能检验本轮机制假设。

不要求每轮都更换阵型，也不要求并行构建多个版本。不得仅以“上一版成绩不错”“改动较少”或“方便比较”为理由自动沿用，也不得为了追求新颖而无理由推翻结构。未测试的结构继续标记为未知。

### 3.3 以“战术机制假设”组织升级，而不是堆砌角色和指令

每项主要升级都必须写成完整链条：

**已观察问题 → 目标战术机制 → 具体配置组合 → 预期改善指标 → 主要副作用/失败条件。**

例如，不能只写“让某位置更多地逼抢”；应说明该位置在 OOP 的实际站位、负责封锁的传球线路、相邻位置如何补位、逼抢失败后谁保护其身后空间，以及用哪些可用指标检查压迫收益和空间代价。

角色/职责、PI、TI、位置转换必须放在同一个协同上下文中审查：
- PI 必须按 IP/OOP 阶段、位置、角色和职责判定，不得把同名 PI 当作跨位置通用规律。
- 角色原生固定开启/关闭的行为必须纳入实际设计，不能把角色行为与可叠加 PI 混为一谈。
- TI 是全队共享设置；评估其对多个位置和两个比赛阶段的共同影响，不得假定它只作用于某一条线。
- 对手指令只在明确针对对手特征且与本队结构相容时使用；不能用 OI 数量替代战术质量。
- 球员属性、熟练度、可用性与位置竞争关系是配置落地条件；球员条件不足时，要区分“战术机制不成立”和“当前阵容执行不了”。

外部 META、论坛战术和公开 FMF 只能提供可研究的机制或候选结构。必须重新检查其 build、测试协议、球员条件、位置职责和本项目约束；不能因为榜单排名高就复制其整套配置，也不能只挑有利数据而忽略其 OOP 结构和风险。

### 3.4 第三层：角色与职责的引擎协同（强制）

本层研究单位不再是单个角色，而是**多个位置的角色/职责组合及其共同跑位结果**。不得只根据某角色单独表现、声望或现实足球职责判断强弱；必须分析它与相邻位置、前后线和 IP/OOP 转换的协同。

每轮正式设计必须建立一份简明的角色协同矩阵，至少检查以下关系：

- **纵深组合：** 中场进攻职责、前腰进攻职责、前锋进攻职责之间，是否形成错层前插、交叉跑动、连续纵深威胁；是否多人同时攻击同一条线路，或都等待脚下球而缺乏身后威胁。
- **肋部组合：** 一名或多名肋部中场与前腰、边锋/内锋、边后卫之间，是否形成不同高度和不同通道的接应；是否占用同一肋部、堵塞传球线路或把中路让空。
- **宽度组合：** 边后卫/翼卫是否提供稳定宽度；边锋/内锋内收后是否有外侧通道接替；两侧是否需要不对称设计；边后卫前插后是否有中卫、后腰或其他位置承担保护。
- **中场连接：** 后腰、中前卫、前腰及回撤前场球员之间，是否有出球点、接应角度、推进者和最后一传；是否出现同层扎堆、纵向断层或无人连接。
- **禁区与二次进攻：** 前锋、后插上中场、边路球员的禁区攻击点是否互补；是否有人负责远门柱、近门柱、点球点/弧顶及二点球；是否因人数过多挤占空间，或人数不足无法形成持续压力。
- **防守与保护：** OOP 第一压迫线、双/单后腰、中卫和边后卫的角色职责是否互相补位；前压角色离位后谁保护其身后与肋部；压迫触发者与封锁传球线路者是否形成协同。
- **攻防转换：** IP 进攻角色转换到 OOP 职责后，球员是否能在丢球时形成有效回收/压迫，得球时又能快速成为接应或纵深出口；不得只看两张静态阵型图。

角色协同矩阵每项至少写清：
1. 参与的位置、IP/OOP 阶段、角色与职责；
2. 预期跑位/占位关系，以及它们如何互补；
3. 可能的冲突、重叠、空档或身后风险；
4. 该组合服务的战术机制；
5. 可从赛季报告观察的指标；若没有直接事件数据，明确标为无法直接观测；
6. 当前状态：已测试、结构级观察支持、待验证或证据不足。

允许研究非传统或高攻击性的组合，例如双肋部中场进攻、前腰进攻与双前锋纵深攻击的协同，以及边后卫持续提供宽度的组合；这些只是可研究的组合类型，不是预设的最佳答案。必须根据角色可用性、职责权限、属性条件和整队空间关系判断是否成立。

**组合效能不得拆分归因：** 多个角色/职责同时形成正向结果时，最多先认定组合级观察支持。除非有足够的可比证据，否则不得宣称某个单独角色或职责是收益来源。角色原生行为和职责对跑位的影响必须纳入解释，不得把角色协同效果误写为 PI 的效果。

### 3.5 第四层：个人指令与球队指令服务于结构（强制）

PI、TI 和 OI 是对既定结构与角色行为的强化、限制或修正手段，不是阵型设计的替代品。设计顺序必须是：**先确定结构与位置关系，再确定角色/职责协同，最后选择 PI/TI/OI。** 不得为了让少数指令看起来合理而反向扭曲阵型或保留不合适的角色组合。

每轮必须检查以下指令机制类别，并明确哪些与本轮结构有关、哪些不适用、哪些因数据不足而暂不判断：

- **分层逼抢：** 区分团队逼抢强度与个人触发频率。检查边后卫/翼卫、后腰/中场、前场球员和中卫是否承担不同压迫任务；谁负责上抢、谁封锁线路、谁保护身后。不能把全队和所有位置一律调到最高档作为默认。
- **积极铲抢：** 将球队层面的凶狠铲抢与球员 PI“更凶狠地铲球”分开评估；结合位置、角色、职责、对抗区域和球员属性判断适用范围。效果观察看有效抢断、球权恢复、对手推进和机会质量，不使用犯规、黄牌或红牌作为战术成效指标。
- **个人压迫频率：** “更多地逼抢/较少地逼抢”必须按 IP/OOP 阶段、实际位置、角色和职责逐项判断。压迫者要有协同补位者；中卫是否减少主动上抢，取决于身前屏障、边后卫站位和身后空间，不得机械套用。
- **传中与落点：** 将传中发起位置、传中者角色/职责、目标落点、禁区攻击者跑位和二点球保护作为一条完整链路检查。后点传中不能只看传中次数；要尽可能核验落点、接应、射门与 xG 事件链。
- **跑位指令：** 前插、拉开宽度、内切、自由跑位、回撤接应等 PI 必须结合角色原生跑位和相邻位置的空间分工；避免多人同时离开关键区域，或多人重复进入同一通道。
- **射门行为：** 更多/更少射门、远射倾向等，必须结合球员所处位置、射门数量与质量、xG/NPxG、禁区内外分布和是否错失更好传球机会评估；不能只看进球数。
- **球队指令：** 比赛节奏、进攻宽度、防线高度、逼抢频率、传球方式、传中方式、反击/重新组织等共享 TI，必须评估其对多个位置与两个比赛阶段的连锁影响。团队 TI 不得被误认为只作用于单一球员或单一区域。
- **对手指令：** 只有在对手特征、比赛计划和本队结构能说明具体目标时才采用；不能以 OI 数量或“全选”替代分析。

每一项被加入、删除或改变的 PI/TI/OI，必须记录：
1. 它要解决的明确问题，以及服务的结构级/协同级机制；
2. 所属 IP/OOP 阶段、位置、角色、职责；球队指令需注明共享影响范围；
3. 与角色原生固定行为是否重复、冲突或被权限禁止；
4. 对相关位置及其队友的预期影响，而不只是对持有该指令球员的影响；
5. 预期收益、可能副作用和 D5 可观测指标；
6. 当前证据等级及是否正式准入。

**指令不得凌驾于结构：** 若某 PI/TI 与阵型空间、角色职责或队友跑位冲突，应优先重新设计角色/职责/位置关系，或撤销该指令；不得继续叠加其他指令来掩盖冲突。若缺少传球线路、压迫事件、传中落点或跑位事件等直接数据，必须说明只能作球队/组合层观察，不能伪造单项效果归因。

### 3.6 允许整套协同改动，但每个改动必须有明确任务

每轮不设修改项数量上限，也不强制单变量 A/B。若解决一个结构问题需要同时调整多个位置、角色、PI 和 TI，应作为一个完整方案一起设计，不得为了满足单变量实验而保留已知冲突。

但不得无目标地同时改动大量设置。所有改动必须回连到本轮问题优先级清单，并分为：
- **主改动：** 直接解决本轮首要问题；
- **配套改动：** 让主改动能够运作或保护其副作用；
- **机会型改动：** 有机制依据但证据较弱，必须明确风险和观察指标。

多项改动同步后，D5 最多先支持“整套方案/结构级观察”，不得把改善平均分配或拆算到每个 PI/TI。若本轮没有可靠证据支持某个改动，就将其标记为待验证，不得写成既定引擎规律。

### 4. 生成下一正式版本 FMF

每轮按唯一父版本构建新的 FMF，不覆盖历史版本。必须核验父版本 SHA-256、IP 四后场位置 DL/DCL/DCR/DR、11 个槽位的 IP/OOP 位置/角色/职责/转换、新角色位置资格和 duty 兼容性、每一条实际选择 PI 的原生权限、TI 原生 bit 向量、style string/FourCC、TAC footer/ID lists/AOM/IMG/opaque 成员保护，以及 FMF 再解析和 read-after-write。

每个阶段对象必须提供 PI 数组，但允许空数组；固定开启 PI 不重复写覆盖位。不得把配置条数、可编辑项和实际序列化 bit 混为一个数字。只有实际执行并通过的检查才能标记 PASS。原生文件回读不等于游戏内导入；游戏内导入不等于赛季实测。

### 5. 正常赛季复盘与下一轮迭代

**持续研发自动推进规则（强制，不得停在复盘）：**

- 这条研发线已由用户明确授权持续迭代。用户提供并确认新版本赛季报告后，完成 D5 分析、四类配置决策、台账写回和 GitHub read-back 后，必须在**同一任务中**自动启动下一代 D0–D3。
- “D5 分析完成/台账已更新”不是本轮任务的终点；正常终点是下一版本完成设计、父子差异、四类决策、原生权限预检、D3 FMF 构建与同次报告核验。
- D4 游戏内导入/显示是独立阶段，允许保持 pending；除非某个实际设计或兼容问题确实依赖 D4 证据，否则 D4 未完成不得阻断下一代 D0–D3。
- 不得等待用户再次发送“继续”“升级”“生成下一代”；不得把下一轮验证目标只写入报告而不执行版本升级。
- 仅在用户明确要求暂停/停止，或遇到真实硬阻断（例如准确父 FMF/recipe 缺失、原生权限拒绝、工作流无法触发、构建无法生成/下载）时暂停。必须说明具体阻断项、已完成阶段和未完成阶段，不得把软性证据不足伪装为硬阻断。
- 每次 D5 后自动生成下一代时仍必须执行第6节：先读台账、核验准确父版 SHA、完整比较 11 槽/22 阶段/PI/TI/opaque/native fields、发布四类清单，再构建。

### 6. 跨版本指令决策台账（强制）

本项目必须维护 [TACTIC_INSTRUCTION_DECISION_LEDGER.md](TACTIC_INSTRUCTION_DECISION_LEDGER.md)，这是 V0.5 起唯一的跨版本配置沿革与效果决策总账。**每次战术迭代都必须查阅；每次赛季报告分析完成都必须回写；每次新 FMF 生成前必须完成父子版本完整差异比较。**

#### 6.1 每次战术迭代开始前：先查阅台账

- 从 GitHub 仓库读取最新台账，确认最新提交/内容版本；不得依赖记忆、聊天摘要或旧副本。
- 读取当前正式父版本、父 FMF SHA-256、对应 recipe 和最近一次 D5 报告结论。
- 明确哪些配置已经准入、哪些只获得结构级观察支持、哪些未准入、哪些已替换或存在原生兼容性问题。
- 不得因为某项配置存在于父版本，就默认它值得留下。

#### 6.2 每次生成新 FMF 前：完整父子配置 diff

必须以准确父版本及其 SHA-256 为基准，对比新子版本的完整配置，覆盖：

- 11 个槽位、全部 22 个 IP/OOP 阶段：阶段位置、位置转换、角色、职责；
- 每个阶段的全部 PI：新增、修改、删除、空数组、角色固定开启项与序列化覆盖位分别记录；
- 完整共享 TI 向量：显式设置、父版继承、清除/重置和 opaque/无法解码位分别列出；
- 心态、原生 style string、FourCC，以及任何其他实际写入的战术字段；
- 角色资格、职责兼容、PI 权限和阵型级限制。

不得仅靠设计说明或 JSON 表面差异推断最终 FMF 字节状态；要与同次 read-back report 核对。无法读取/解码的字段必须标成“未解析/证据不足”，不得假定没有变化。

#### 6.3 每次迭代必须给出四类配置清单

每个正式版本的设计审计、构建前摘要和台账记录，都必须明确列出以下四类；具体到配置 ID、位置/阶段、原值→新值、依据与状态：

1. **继承保留**：父版本中有意不变并继续带入子版本的设置。注明为什么保留，并标记证据级别。只有达到“位置最优”或“显著正收益”门槛才可称为“已准入”；仅为维持协同结构而暂时沿用的，要明确写“结构性/临时沿用，单项未准入”。
2. **替换淘汰**：父版中本轮改值、删除或退役的设置。保留旧值、新值/移除状态、替换原因、支持证据和风险；不能删除历史记录，也不能把“替换”写成已证明旧值在所有情境无效。
3. **新增待验证**：本轮新加入的角色、职责、位置转换、PI、TI 或结构。说明设计假设、预期收益、风险及下一份 D5 报告的验证指标；D5 前不得标记成功。
4. **证据不足**：当前无法证明最优/显著收益，或数据字段/角色码/版本映射/解析兼容性不足的候选。说明是否暂不采用、是否需专项核实；不得默认为继承保留或有效。

四类是每轮必须出现的**顶层分类**。如果某项配置因协同需要仍被带入子版本，但单项效果没有证据，应列在“继承保留”，并明确标为“结构性/临时沿用，单项未准入”；如果它没有被有意带入，则列在“证据不足”或“替换淘汰”，不得含糊处理。原生角色/阵型兼容性不合格属于必须淘汰/修正的技术阻断项。

#### 6.4 每次赛季数据分析完成后：立即回写台账

- 当用户明确确认报告版本后，先完成原始数据、覆盖、build/schema、整体/主客场/胜平负、进攻、防守、推进、球员以及归因边界分析。
- 在同一项任务内，将报告身份/链接/run ID、使用版本、存档 SHA（可得时）、FM27 build、样本范围、数据覆盖与局限、关键观察、与父版对照、逐项去留决策、四类配置摘要和下轮验证目标写入台账。
- 若某项 PI/TI 没有足够证据，保持“证据不足/未准入”；若整体组合表现值得继续测试，可记录“结构级观察支持”，不能把组合收益拆给单项。
- 即使本轮没有触发任何配置修改，也必须追加一条对应报告的复盘记录，明确“无配置状态变化”及其原因，不得省略台账回写。
- 提交后重新读取 GitHub 上的台账，核验报告条目、版本映射和四类清单确实存在；只有 read-back 成功后，才可对用户说该赛季分析和台账同步完成。

#### 6.5 每次 D3 构建后的身份回写

D3 构建成功后，必须更新台账对应版本记录：父版本及父 FMF SHA、子版本/recipe SHA、build request commit、Actions run/workflow ID、artifact ID/name（若可取得）、FMF 文件名/字节数/SHA-256、same-run report SHA-256、实际 read-back 检查结果，以及 D4/D5 尚未完成的状态。详细构建说明可保存在 `*_BUILD_REPORT.json` 和 `*_DESIGN_AND_AUDIT.md`，但台账必须保留可定位的身份索引。若 D3 失败，也要记录失败 run 与阻断原因，不得把失败或未取得的 artifact 标成完成。

## 三、数据与证据纪律

### 数据质量与标准化

- 记录真实样本覆盖与解析兼容性风险。schema 布局借用、目标 build 未上游登记等情况应如实标记；总量对账通过不代表每个字段语义都已获上游认证。
- 胜/平/负组列出场次、比分和每场均值，避免只比较总量。
- 主/客场同时比较我方和对手表现，避免只看控球或单向传球数。
- 球员数据尽量按分钟/每90分钟；样本太少时标出分钟与出场数。
- 前场三区传球、传中、推进传球等原始计数，应按每场、每90、每100次总传球或控球时间归一化；拿不到分母时只作描述性信号。
- xG 与 NPxG、实际进球与预期进球需分开；若数据源把点球纳入 xG，不能把它直接当作纯运动战终结效率。
- 对手实际失球与 xGA、我方实际进球与 xG 的差值只能说明结果转化偏离预期，不足以独立证明运气、门将或某个战术字段的责任。
- 犯规、黄牌和红牌一律不纳入战术评价。

### 证据类别

1. 报告直接观察：原始比赛、球员或配置文件中可复核的事实。
2. 关联现象：结果分组、主客场或球员表现存在的统计差异。
3. 机制依据：FM27 当前 build 的引擎研究、原生设置和外部可复核战术资料。
4. 设计假设：根据以上信息提出的 V0.x 配置方案，等待新版本正常赛季复盘。

### 效能证据与正式准入门槛（强制）

“配置已写入”“FM27 能导入”“赛季表现不错”和“某项配置有效”是四种不同结论，必须分别记录。按以下层级表述：

| 证据状态 | 可支持的结论 | 不允许的结论 |
|---|---|---|
| 配置/原生回读通过 | 该角色、职责、PI、TI 或字段确实写入 FMF | 不能说明游戏内已接受，更不能说明战术有效 |
| D4 游戏内导入与重开核对通过 | 游戏接受并显示该配置 | 不能说明比赛表现提高 |
| 单份 D5 报告出现正向变化 | 本版本在该样本中出现正向观察/关联 | 不能称为单项有效、最优或因果 |
| 多项协同变化后出现正向结果 | 该整套方案出现组合级/结构级观察支持 | 不能把收益拆给其中某条 PI/TI 或单个角色 |
| 可重复的结构级结果 | 同一结构在独立 D5 样本或可复现测试中多次呈现相同方向 | 不能自动证明每个组成指令单项有效 |
| 可定位的单项对照/位置级证据 | 在适用位置、角色、职责与 build 条件下，某配置相对可比替代方案表现更好 | 不得外推为所有位置、球员、对手和 build 都有效 |
| 满足重复性与代价审查的证据 | 可按下述规则正式准入 | 不得把准入解释为永远不需复核 |

“位置最优”必须有可比较的替代配置：在相同或足够接近的 build、阵容/球员条件、比赛协议和位置职责下，对同一战术槽位的可行选项进行比较；并且位置/角色数据的身份映射与覆盖可靠。没有可比替代项，或无法确认球员实际承担该位置/角色时，不得称为“位置最优”。

“显著正收益”不得只凭某一赛季积分或进球增加认定。至少应满足：
1. 目标指标与本轮设计假设事先对应，且改善幅度具有实际战术意义；
2. 在至少两个相互独立的 D5 样本，或有相同初始状态与可复现条件的重复测试中，主要改善方向一致；
3. 至少有一组机会质量/战术过程指标支持目标机制，而非只出现比分或转化率变化；
4. 检查 xGA、对手绝佳机会、主客场差异和其他关键代价，没有足以抵消收益的系统性恶化；
5. 已排除明显的 build、阵容、版本映射、样本范围和解析覆盖混杂因素。

若数据量或测试协议不足以计算统计显著性，不得伪称统计学显著；可以写“重复性正向观察”或“组合级支持”。一份 38 场赛季报告只能作为一个 D5 样本，不因比赛场次达到 38 就自动变成重复验证。

正式准入分为三个层面：
- **结构级准入：** 整体 IP/OOP 结构或协同组合达到重复性正向标准；只准入该结构/组合，不向内拆分单项。
- **位置/角色级准入：** 证据能可靠定位到具体位置、角色与职责，并达到可比较的“位置最优”或重复性正收益标准。
- **单项 PI/TI 准入：** 必须有能定位到该指令的对照或足够强的独立重复证据；多项同步变化产生的整队结果不满足此条件。

不要求每轮都进行 A/B 或重复实验。若用户当前只有单份赛季报告，照常完成整套战术升级，但结论按证据层级标为“单样本观察/组合级支持/待验证”，不因此阻断设计，也不虚构单项准入。只有在用户明确要回答某条指令的独立效果，且现有证据无法回答时，才提出专项对照测试。

尚未达到准入门槛不意味着永远无效；若为维持整体协同而暂时沿用，必须在台账“继承保留”中标明“结构性/临时沿用，单项未准入”。证据不足且未被有意沿用的项目列入“证据不足”，不得自动继承。此规则不要求每轮进行单变量 A/B；允许根据整体诊断做多项协同改动。

### 外部资料

每轮结合当前 FM27 build 检索引擎更新、测试榜单、社区实测和原始 FMF。记录游戏 build、日期、样本量、测试协议和指标。不同网站、不同 build、不同对手/球员协议的数据不可直接混排。榜首战术可提供机制线索，但不能直接替代有球四后卫目标，也不能复制整套配置。

## 四、原生 FMF 与模板/载体规则

当前空 style string 与 FourCC 4c4c554e 是 V0.8 原生父快照的已验证格式身份。它们作为当前兼容默认值保留，不是战术性能规律，不代表空风格字段或特定 FourCC 能提高比赛表现。除非用户明确授权探索其他原生身份，否则不擅自更改；若开展新身份实验，必须独立核验游戏导入、字段完整性和对照版本，不得把格式兼容结果写成战术收益。

必须区分官方风格样本和原生快照载体：

- 官方风格是已登记的原生 TAC style string / FourCC / 样本。
- 原生快照载体来自特定父版本的 FMF，载体本身可能包含实际战术配置，不能称作空白战术。
- 当配方显式写出完整 22 个 IP/OOP 阶段时，阶段位置/角色/职责/PI 按配方重建；共享 TI 向量则从父快照开始，仅写入配方中声明且已映射的 TI 变化。未声明的 TI/opaque bits 可能继续继承父快照，必须明确记录，不得声称全部 TI 已覆盖。
- 每轮记录载体路径、载体 SHA、配方显式覆盖项、继承项及实际写入/回读的完整 TI 向量。

## 五、D0–D5 生命周期与版本身份

| 阶段 | 含义 | 通过条件 |
|---|---|---|
| D0 | 战术目标与完整 IP/OOP 设计 | 明确有球 DL/DCL/DCR/DR；说明全队协同和风险 |
| D1 | 原生兼容核对 | 位置/角色/职责及所有实际选择 PI 的原生权限通过 |
| D2 | 结构化配方 | 11 槽、22 阶段对象、必需字段、TI 和风格登记通过；PI 数组允许为空 |
| D3 | 原生 FMF 构建 | 指定 run 生成 FMF 和同次 report；二进制回读、大小和 SHA 核验通过 |
| D4 | 游戏内导入与显示 | 在 FM27 内成功导入；检查 IP/OOP 位置、角色、职责、PI、TI 和战术身份显示 |
| D5 | 比赛/赛季表现 | 取得明确版本映射和质量合格的比赛/赛季数据，按本规范分析收益与副作用 |

D3 是单次原生 FMF 构建的技术交付门槛，不是战术效果验收。D4 只能证明游戏接受并显示了设置，不证明比赛行为有效。D5 才能评价实际比赛表现。未执行的阶段必须明确标记为未验证/待验证，不得自动视为通过。

### 版本与构建唯一身份

每个版本除人类可读标签（如 V0.9）外，必须记录唯一 build identity：唯一父版本及其 SHA-256、当前 recipe 路径与内容 SHA-256、build request commit、Actions workflow/run ID、artifact ID/name、FMF 文件名/字节数/SHA-256、同次 report 路径/SHA-256、FM27 build 与数据报告来源。不得把同一个 V0.x 标签用于两个不同配方或不同构建而不加草案/修订/run 标识。

历史候选不删除，但必须显式标记草案、撤回或被哪个正式版本取代；默认正式版本由唯一的 recipe、FMF、same-run report 和 build identity 绑定。文件名、摘要、链接、哈希和实际文件必须一致。

## 六、报告触发与交付

当用户在本项目中说明新赛季报告已放入仓库、已上传或可以分析时，自动执行本规范五步流程，不得只回复收到，也不得要求用户重复已确认的版本映射。若报告路径或版本归属仍无法确定且会实质改变结论，才询问一个必要问题。

每轮输出至少包括：样本/数据质量、整体优势与弱点、关键球员表现、外部机制交叉依据、战术设计决策、角色/PI/TI 协同矩阵、唯一父版本、下一版本 recipe、原生 FMF 与同次 report、D0–D5 各阶段状态，以及跨版本决策台账的更新和本代去留摘要。纪律数据排除。


## 七、总账同步门禁（2026-11-26起强制执行）

**每一次战术迭代都必须更新总账；这不是可选的文档整理工作。** 本节覆盖此前任何“只更新迭代日志/只更新版本目录即可”的宽松做法。

### 7.1 每轮更新的固定文件
1. `TACTIC_INSTRUCTION_DECISION_LEDGER.md`：先查旧账，再更新本轮逐项配置沿革和四类决策。
2. `ITERATION_LOG.md`：追加父子版本、所有实际变化、保留项、设计假设、构建身份和D0–D5状态。
3. `VERSION_CATALOG.md`：更新当前版本、结果排名、文件链接、哈希和验证状态。
4. `SOURCE_REGISTER.md`：登记用户确认的Exporter Run、原始URL、存档SHA、build、覆盖及解析限制；没有D5报告则登记“待实测”，不得伪造来源。
5. 本轮设计审计、构建报告、赛季分析文件：保存完整细节，并从上述总账链接。

### 7.2 更新时点
- **D0设计前：** 读取最新总账、版本目录、父recipe/FMF和最近D5报告；形成父子diff与四类决策草案。
- **D1–D3构建后：** 将真实recipe/FMF/report身份、哈希、Actions run/artifact及检查结果写入总账与版本目录；只写实际取得的数据。
- **D4游戏导入后：** 更新导入状态及游戏内核对差异；未由用户确认的不得标记通过。
- **D5赛季报告后：** 更新成绩、数据质量、四类决策、配置级证据状态和下一轮目标；同一轮自动进入下一版本D0–D3，除非用户明确暂停或出现硬阻断。

### 7.3 发布前一致性检查
- 四份核心文件的版本号、父版本、Run ID、FMF SHA、D0–D5状态必须一致。
- 每个PI记录必须包含阶段、位置、角色、职责和PI值；每个TI记录必须包含指令组和值。
- 继承保留必须区分“已准入”与“结构性暂留/单项未准入”。
- 替换淘汰必须记录旧值→新值；不能写成跨情境普遍无效。
- 新增待验证必须有目标指标、风险和失败条件。
- 证据不足必须明确未知原因和后续处理；不能用整队积分替代单项证据。
- D3/D4/D5严格分开；缺失项写pending/unknown，不得推定。
- GitHub更新后逐个read-back；只有所有核心文件的read-back均通过，才可报告“总账已更新”。

### 7.4 历史资料规范化策略
- 不覆盖历史原始报告，不猜测缺失Run ID、FMF哈希或配置字段。
- 旧版本未能取得recipe/FMF或逐项diff的字段标为“历史资料缺失/待补录”，不伪造完整性。
- 本总账顶部“当前权威视图”优先于未更新的历史快照；后续整理旧版本时逐轮补齐，不能一次性把未知值补成确定值。
