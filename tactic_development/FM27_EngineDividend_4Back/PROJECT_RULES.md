# FM27 EngineDividend 4Back｜正式项目研发规则

> **最高目标：PPG ≥ 2.85。** 本文件是本项目规则入口；机器可读参数见 [PPG_TARGET_POLICY.json](PPG_TARGET_POLICY.json)。规则只约束本项目目录内的研发，不改变 FM-TA 通用工具。

## 1. 唯一最高目标与评价方式

本项目的唯一最高研发目标是：在用户管理球队的联赛赛季中达到 **PPG ≥ 2.85**。

`PPG = 联赛总积分 ÷ 已完成联赛场次`

- 38 场联赛至少需要 109 分才能达到 2.85 PPG。
- 目标是研发方向，不是对任何单次赛季结果的保证。
- 每轮优先判断是否提高稳定赢球和积分能力；进攻、防守、机会质量、主客场表现用于解释 PPG 的来源、代价和可持续性。
- 不把某个历史版本的 xGA、进球数、阵型或角色组合设为高于 PPG 的独立终点。
- 不允许为降低 xGA 而无条件牺牲胜率，也不允许以短期高转化掩盖机会控制崩溃。

## 2. 项目硬约束与开放搜索空间

- IP 有球阶段必须且只能包含四个后场位置槽：`DL`、`DCL`、`DCR`、`DR`，每个恰好一次。
- IP 其余七个位置、IP 阵型数字形态、角色、职责、PI、TI、心态均开放。
- OOP 无球阶段阵型、人数、角色、职责、PI、TI、心态及 IP↔OOP 转换均开放；不得误写成 OOP 必须四后卫。
- 每轮只形成一套主线完整战术。可以保留已有独立探索分支，但不得把多套候选交给用户代替研发决策。
- 阵型改变不是禁区；但必须说明它针对什么问题、依据哪些本队/外部证据、预期改善什么 PPG 相关环节、有什么风险，以及如何验证。
- V0.5 是历史起点，不是必须复制的阵型模板；V1.3、V1.6、V1.7、V1.8、R1、R2均是证据来源，不自动成为下一版模板。

## 3. 每轮强制决策流程

必须按顺序完成，不能先生成后补理由：

1. **历史回溯：** 每轮固定以 V0.5 原始 FMF 为唯一重生基准（SHA-256 `e9a82cf273187b20567c38e25f362e7aed4e2a38ac525789c69d7abf641c7257`），读取权威总账、全部历史 recipe/审计/D5 报告和版本目录；不得将最近版本、最高分版本或最近 D5 版本自动设为父版。
2. **PPG 问题诊断：** 分析胜平负、积分/PPG、进失球、xG/NPxG、xGA、双方绝佳机会、主客场、平局和失利；区分机会创造、机会控制、结果转化和执行因素。
3. **问题优先级：** 选择最可能限制 PPG 的主问题；不得仅因某项指标变化就自动修改战术。
4. **机制与结构研究：** 比较继续现有结构、局部重构和整体重构；结构改变必须有明确证据链。外部 META 只能产生假设，不能替代本队赛季验证。
5. **四类决策：** 每轮必须完整列出：
   - 继承保留
   - 替换淘汰
   - 新增待验证
   - 证据不足
6. **唯一方案设计：** 每项主改动写明“问题 → 机制 → 配置 → 对 PPG 的预期路径 → 风险/失败条件 → D5 指标”。
7. **生成前审计：** 核对 IP 四后场、11 槽/22 阶段、完整角色职责/PI/TI/心态、父版身份与 SHA、历史冲突和四类决策。
8. **构建与独立回读：** 通过项目专属入口后，才调用 FM-TA 原生预检和 FMF 生成能力。
9. **归档与复核：** 更新唯一总账、迭代日志、版本目录、来源登记及本轮审计；提交后 read-back。
10. **实战状态：** D3 只表示离线构建/回读；D4 是游戏内导入；D5 是用户确认版本映射后的赛季报告。三者不得混淆。

## 4. 四类决策和证据等级

每项配置必须归入且仅归入以下一类：

| 类别 | 规则 |
|---|---|
| 继承保留 | 说明继承原因和证据等级；结构性暂留不等于单项已验证 |
| 替换淘汰 | 记录旧值→新值/移除、原因及适用范围；不夸大为所有情境无效 |
| 新增待验证 | 写明假设、预期收益、副作用、失败条件和 D5 指标 |
| 证据不足 | 明确未知内容、缺失数据及是否暂不采用；不得默认为有效 |

证据至少区分：报告直接观察、统计关联、当前 build 外部研究/原生机制、设计假设。多项同时改动只允许先归因到组合层，不得虚构单项因果。

## 5. PPG 导向的分析纪律

- 第一评价指标是联赛 PPG；同时报告总积分、胜/平/负和胜率，避免单看积分总量。
- 进攻评估必须区分 xG/NPxG、绝佳机会、实际进球与转化差额。
- 防守评估必须区分 xGA/对手绝佳机会与实际失球；不能把失球高于 xGA 直接归因于阵型。
- 必须分析主客场差异，以及平局/失利中的机会质量和结果转化。
- 以用户确认的实际战术版本映射为准，不推测每场使用的 tactic。
- 不同存档/随机种子不构成受控 A/B；样本、数据覆盖和解析限制必须明确。
- 犯规、黄牌、红牌不得作为战术质量指标。
- PPG 未达目标时，按诊断结果选择下一轮方向；不允许机械地只改防守或只改进攻。

## 6. 生成前必须通过的项目审计

项目审计至少检查：

- 项目策略文件存在，目标明确为 PPG ≥ 2.85。
- 唯一权威总账已写入 PPG 2.85 目标。
- 本轮设计审计明确写出 PPG 2.85、父版本及 64 位父 FMF SHA-256。
- 四类决策全部出现。
- 写明下一轮 D5 可量化验证指标。
- recipe 含 11 个槽位，每槽均含 IP/OOP 阶段对象。
- IP 位置集合中 DL、DCL、DCR、DR 各恰好出现一次。
- 通过后再调用 FM-TA 原有 catalog-backed preflight；该工具负责原生角色/职责/PI权限等通用技术检查。
- 任一项目审计失败，禁止继续调用生成器。

审计通过不等于战术效果通过；它只说明设计与项目硬规则完整，随后仍需 D1–D3 技术验证、D4 游戏内确认和 D5 赛季验证。

## 9. 项目专属构建命令

在仓库根目录运行（PowerShell / Python 3.12）。先把父版本 FMF 的真实路径填入 `--parent-fmf`：

```powershell
py -3.12 tactic_development\FM27_EngineDividend_4Back\build_project_tactic.py `
  --recipe tactic_development\FM27_EngineDividend_4Back\<本轮配方>.json `
  --audit tactic_development\FM27_EngineDividend_4Back\<本轮设计审计>.md `
  --parent-fmf D:\<父版本>.fmf `
  --output tactic_development\FM27_EngineDividend_4Back\builds\<本轮版本>.fmf `
  --report tactic_development\FM27_EngineDividend_4Back\builds\<本轮版本>.report.json
```

设计审计中的父 FMF、recipe、项目规则、决策总账和 PPG 策略 SHA-256 必须与当前实际文件一致。每次规则或总账变更后都要重新制作审计。可用 `Get-FileHash -Algorithm SHA256` 分别读取这些文件的哈希，再填写审计文件：

```powershell
Get-FileHash 'D:\<父版本>.fmf' -Algorithm SHA256
Get-FileHash .\tactic_development\FM27_EngineDividend_4Back\<本轮配方>.json -Algorithm SHA256
```

执行顺序固定为：校验父 FMF 与配方 SHA-256 → 项目 PPG/历史规则审计 → FM-TA 通用 catalog 权限预检 → FM-TA 原生 FMF 生成。项目审计失败即退出，不调用后两步；配方、审计和输出必须在项目目录内，输出已存在时拒绝覆盖。

运行项目门禁回归测试：

```powershell
py -3.12 -m unittest discover -s tactic_development\FM27_EngineDividend_4Back -p test_project_iteration_gate.py
```

项目审计是本项目正式迭代的唯一强制门禁；构建执行器可以有多个合规实现。直接调用 FM-TA 通用生成器而未先通过项目审计，即使成功生成 FMF，也不构成本项目完成一次合规迭代。通过项目审计后，可由项目专属入口或 [GENERATION_EXECUTION_POLICY.md](GENERATION_EXECUTION_POLICY.md) 规定的离线原生生成路径完成 D3。



## 2A. 最高优先级设计原则：主动制造引擎行为错位（强制）

**本项目不以现实足球理论作为战术设计边界；必须主动探索“指令、角色、位置与实际引擎行为错位”所产生的非传统收益。** 这是研发方法的硬规则，不是可选风格建议。

1. 不得用现实足球中的“合理站位、标准职责、传统位置分工、攻守平衡、教练理念”否决一个在 FM27 中可能有效的组合。现实足球常识只能用于提出待验证问题，不能充当淘汰依据。
2. 每轮设计必须主动寻找至少一组可解释的行为错位假设，研究维度包括但不限于：
   - 阵型位置槽与球员实际移动/占位行为错位；
   - 角色默认行为与 PI/TI 明确指令错位；
   - 角色职责与其所在阶段任务错位；
   - IP 与 OOP 角色/位置转换造成的行为错位；
   - 球员名义位置、接球区域、跑动通道、压迫对象和实际防守责任错位；
   - 进攻/防守阶段切换时，对手 AI 的盯防、压迫、补位或阵型重组与我方行为错位。
3. 设计审计必须写清：**预期错位是什么 → FM27 引擎可能如何执行 → 对手 AI 可能如何响应 → 预期产生何种空间/人数/跑动/接球优势 → 如何转化为 PPG → 失败条件与 D5 观测指标**。只写“非传统”“引擎红利”而没有具体行为链，不算完成设计。
4. 允许主动测试现实足球中看似不合理、甚至相互矛盾的角色/职责/PI/TI 组合；不得为了视觉合理性而把错位改回传统配置。合法性由 FM27 原生目录/权限检查，效果由比赛引擎与赛季数据验证。
5. 错位是假设，不是先验有效结论。必须区分原生机制已确认、外部样本观察、本队统计关联和本轮设计假设；不得把推测写成引擎事实。
6. 不要求每轮为了形式强行堆叠多条 PI 或制造无意义冲突。错位必须有明确机制假设和 PPG 收益路径；没有可解释收益的冲突配置不予采用。
7. 不把 V1.3 或其他历史高分版本当作现实合理的默认模板。历史版本只用于识别哪些行为错位可能成功、哪些结构/指令组合曾伴随崩溃，再从引擎行为重新设计。
8. IP 唯一硬约束仍是 DL、DCL、DCR、DR 四个后场位置槽各一次；这只约束位置槽，不约束四名球员的实际跑动、角色行为或进攻参与方式。OOP 完全开放。

**违反本节：本轮设计审计不通过，不得生成 recipe/FMF。**


## 10. 构建执行通道不得成为研发阻断（2026-11-26 修订）

**强制原则：严格门禁约束设计与生成顺序，不限制合规生成方式。不得把工具接口的执行能力误写成项目规则。**

- GitHub API/聊天连接器是否能直接执行 Python、是否能 dispatch 某个 workflow，是当前执行环境的能力信息，不是战术设计失败、项目审计失败或 FMF 技术失败。
- 助手不得再以“当前 GitHub 工具只能读写仓库，不能执行项目脚本”作为停止正式迭代、拒绝生成或要求用户重新提供资料的理由。应继续寻找当前可用的本地执行、附件工作区、项目专属 runner 或离线生成方式。
- 标准路径：先运行项目审计，再运行原生 catalog/preflight，再由项目构建入口生成并独立回读。
- 离线路径：当标准入口在当前执行环境不可调用时，仍必须先运行同一份 `validate_project_iteration.py`；通过后，调用 `04_离线原生FMF生成器/FM27GEN1_Offline_FMF_Generator.py`（或其 `build_fmf_from_recipe` API），传入本轮 recipe、catalog、输出和 report。该原生生成器必须完成角色/职责/PI权限、11槽/22阶段、FMF 二进制回读；有可用的通用 preflight 时仍应先执行。离线路径不是跳过审计的旁路，而是同一门禁后的等价执行器。
- 任何执行器都不得修改或弱化本轮设计、不得静默删改 PI/TI、不得覆盖历史产物。若生成器拒绝配置，必须返回具体原生权限/格式错误，再修正设计或映射；不得因现实足球理论而回退设计。
- 通用 Actions 若未执行本项目审计，不得用于本项目正式构建。不得为解决执行器问题而修改 FM-TA 通用生成器、通用工作流或仓库全局规则；本项目的规则与辅助脚本只放在本目录。
- 只有在所有可用执行通道均实际不可用，或缺少生成所必需的真实文件/原生字段时，才可报告具体阻断。报告必须说明已尝试的执行路径、精确错误、已完成阶段和唯一恢复动作；不能把接口能力限制包装成战术/项目限制。
- D3 仍必须以真实生成的 FMF、同次 report、独立回读结果和 SHA-256 为依据。没有真实产物不得宣称生成成功。


## 11. 最高优先级：每轮从 V0.5 重生，不沿最新版本递进（强制覆盖规则）

**本节优先级高于本文件中任何“当前父版本”“唯一父版本”“版本链继承”或类似旧表述。下一轮及以后每一轮均必须执行本协议，不得只在口头说明中承诺。**

1. **固定重生源：** 每轮战术设计与生成的唯一原始基准是 V0.5 原生 FMF：`V21_Leaderboard_TeamInstructions(1).fmf`，SHA-256 `e9a82cf273187b20567c38e25f362e7aed4e2a38ac525789c69d7abf641c7257`。每轮从该原始配置重新构造完整 11 槽/22 阶段，不以 V1.8、V1.9 R2 或任何最新版本作为 recipe/FMF 父版。
2. **历史经验全部回看：** V0.6 及之后所有版本均是历史实验档案。每轮必须从 V0.5 出发，系统审查全部历史版本的 D5 成绩、配置差异、构建审计和失败/风险记录；有价值的经验可以移植，但必须说明证据、适用条件及为何适用于本轮。
3. **不是复制 V0.5：** 重生不等于原样复制。每轮必须重新做“继承保留、替换淘汰、新增待验证、证据不足”四类决策，允许整体重构 IP/OOP、位置、角色、职责、PI、TI 和心态；只有项目明确锁定的原生身份字段继续保持。
4. **父版字段定义：** 设计审计中的“重生基准”必须写 V0.5 和上述 SHA-256；“父版本”字段也必须为 V0.5。历史参考版本另列为“历史经验来源”，不得写进父版本字段。父 FMF 路径必须指向与该 SHA 完全匹配的 V0.5 原始文件。
5. **版本编号不等于父子继承：** 新迭代编号可继续递增以保持档案唯一性，但版本号递增不意味着从上一个编号版本继承 FMF。每轮都必须记录“从 V0.5 重生”。
6. **生成门禁强制执行：** `validate_project_iteration.py` 必须校验父版本严格等于 V0.5、父 FMF SHA 等于上述固定值，并要求审计含重生基准字段；任何 V1.x 父版、哈希不符或字段缺失均 FAIL-CLOSED，不得生成。
7. **交付归档：** 每轮审计必须列出历史经验来源、四类决策、V0.5→本轮的完整配置差异、实际 FMF SHA-256 和独立回读。不得把历史版本成绩移植为本轮成绩，也不得宣称未完成的 D4/D5。
8. **下一轮重复：** 用户提交下一份赛季报告后，先回到同一 V0.5 原始基准，结合本轮及此前全部历史证据重新设计；不得把本轮 FMF 自动设为下一轮父版。

**违反任意一条：项目审计失败，禁止生成 FMF。**
