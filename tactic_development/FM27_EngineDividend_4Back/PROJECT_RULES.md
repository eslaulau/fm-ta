# FM27 EngineDividend 4Back｜正式项目规则

> 本文件是项目总规则入口。固定战术边界以 [TACTIC_FIXED_CONSTRAINTS.md](TACTIC_FIXED_CONSTRAINTS.md) 为准；研发循环以 [UPGRADE_GATE.md](UPGRADE_GATE.md) 为准；构建执行以 [GENERATION_EXECUTION_POLICY.md](GENERATION_EXECUTION_POLICY.md) 为准；历史配置以 [TACTIC_INSTRUCTION_DECISION_LEDGER.md](TACTIC_INSTRUCTION_DECISION_LEDGER.md) 为准。

## 1. 项目目标
研发一套利用 FM27 比赛引擎机制的有球四后卫战术，不以现实足球合理性作为设计限制。最终验收目标：完整38场联赛赛季至少109分（PPG≥2.85），且球队 xG≥100。未取得完整赛季证据前，不得宣称达标。

## 2. 固定边界
必须遵守 [TACTIC_FIXED_CONSTRAINTS.md](TACTIC_FIXED_CONSTRAINTS.md)：IP阵型仅限4-2-3-1、4-3-3、4-1-2-3；OOP位置映射、心态4及红框团队指令固定；仅允许调整球员角色/职责、PI及非红框TI。不得擅自改变红框值或固定位置。

## 3. 设计与证据
- 只使用本项目内部历史战术、配方、构建报告和赛季报告作为设计参考；不搜索、不引入外部战术或外部战术资料。
- 不强制从V0.5重新开始。每轮从内部历史总账选取真实父版本或多个配置组件，记录父版本、文件路径和SHA-256。
- V0.5可以作为原生FMF序列化技术载体，但不得因此登记为战术父版。
- 不复制单一历史战术；应结合内部证据进行新的结构与指令组合，并明确待验证假设。
- 四类决策必须完整记录：继承保留、替换淘汰、新增待验证、证据不足。证据不足不得伪装为已验证有效。

## 4. 赛季分析
每轮读取用户明确指定的战术版本和完整赛季报告。不得由导出器自行猜测每场实际使用的战术。分析整体积分、进球/xG、防守/xGA、机会质量、输球/平局和关键比赛；逐位置、角色审查贡献与代价，并与内部历史版本横向比较。数据缺失必须标记，不得推断补齐。

## 5. 生成与验收
- 设计完成后直接进入原生角色/职责/PI权限预检、结构检查、FMF生成和独立回读。
- 不存在D0设计门禁、D0机器清单或D0阻断步骤。不得恢复 validate_project_iteration.py 或类似的D0拦截器。
- 原生权限预检只负责检查游戏原生目录允许的角色/职责/PI；不得代替战术设计判断，也不得扩展为项目规则门禁。
- D1-D3只代表构建技术事实；D4代表用户游戏内导入核验；D5代表完整赛季结果。阶段状态不得混淆，不得虚报。
- 构建失败应报告具体技术错误并修复；不得静默删改用户设计指令或覆盖历史产物。

## 6. 文件与历史
所有历史版本、配方、FMF、报告和赛季分析保留在项目目录和总账中。历史文档中旧D0流程只作为当时的历史记录，不构成现行规则。现行规则冲突时，以本文件及上述专项权威文件为准。

## 7. 冲突优先级
1. 用户最新明确指令；
2. TACTIC_FIXED_CONSTRAINTS.md（固定边界）；
3. PROJECT_RULES.md（总规则）；
4. UPGRADE_GATE.md（研发流程）；
5. GENERATION_EXECUTION_POLICY.md（构建流程）；
6. 决策总账、版本目录和历史记录。
