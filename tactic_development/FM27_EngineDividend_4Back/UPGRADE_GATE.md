# FM27 引擎红利四后卫｜连续赛季研发闭环（最高执行入口）

> 本文件定义项目每一轮的实际工作流。用户提交一份新的战术赛季报告，默认意味着启动一轮完整的“赛季复盘 → 历史总账联动 → 引擎红利研究 → 整体战术升级 → FMF交付”任务；这不是几个可以彼此独立结束的任务。

## 1. 唯一研发循环

`用户提交新赛季报告 → 数据身份与质量核验 → 完整赛季诊断 → 历代总账联动 → 引擎红利与外部实测研究 → 四类决策 → 整体战术重设计 → 唯一FMF构建与核验 → 全部归档 → 等待下一份赛季报告`

- **报告是入口，FMF升级是本轮研发的交付终点。** 不得只完成报告分析后就把“是否升级”留给用户再次提出。
- 分析报告、总账对比、外部研究、设计审计、recipe、build request、FMF和构建报告必须属于同一轮、同一个版本链。
- 前一阶段的观察、证据、问题优先级和四类决策必须直接传递到下一阶段；不得在设计阶段重新开始、丢失或绕开分析结论。
- 新版本进入游戏后的表现，只有在用户提交下一份赛季报告后才能进入下一轮D5复盘。不得把构建成功误称为实战成功。
- 默认执行完整闭环。只有用户明确要求“仅分析/暂不升级/暂停”，或存在阻止继续的真实硬阻断，才可在中途结束。若受阻，必须说明具体缺口、已完成阶段、未完成阶段和恢复条件。

## 2. 输入、版本身份与数据质量

收到报告后，先识别并记录：
- Exporter Run ID、原始报告链接、存档标识/SHA（若提供）、FM27 build、导出器版本、报告日期。
- 用户确认的该报告实际使用战术版本及其 recipe/FMF/构建身份。
- 联赛、杯赛、洲际赛事及各自比赛数量；不得混合不同赛事口径。
- 球队统计、球员统计、身份匹配、位置/角色映射、统计对账、缺失/重复记录、解析器兼容状态。

版本归属规则：
- 只有用户明确确认的版本映射才可用于战术归因。文件名、最新构建版本、时间接近或助手猜测均不能代替确认。
- 若报告映射未确认：仍可完成报告本身的描述性数据审计和不依赖战术归属的统计分析；但必须把战术归因标记为“未确认”，并在无法确定父版本/当前战术身份时暂停生成升级FMF，直到身份得到确认。
- 数据覆盖不足不意味着整轮分析停止。应按可信层级继续：可用球队数据就分析球队层面；球员身份可靠才分析球员；位置、逐场槽位和角色映射可靠才归因到位置/角色/PI。缺失内容标为“未观测/证据不足”，不得补猜。
- 同一存档反复回滚测试、不同随机过程、共同赛程等情况必须按实际设计说明；非同seed比较不得写成受控A/B或单项因果证明。

## 3. 第一阶段：完整赛季报告诊断（D5复盘）

分析必须覆盖报告实际提供且语义可靠的全部关键领域：
1. **比赛结果：** 胜/平/负、积分/PPG、进失球、净胜球；分联赛/杯赛/洲际赛事，主场/客场。
2. **进攻：** xG/NPxG（注明口径）、射门与射正、绝佳机会、禁区威胁、创造与终结效率、实际进球相对预期的差额。
3. **推进与组织：** 后场出球、中场连接、向前传球/持球推进、进入前场三区和禁区、边中路供给与前场接应。原始次数应尽可能按每90分钟、控球或总传球量归一化。
4. **防守机会控制：** 对手射门/射正、绝佳机会、xG/xGA、禁区威胁、对手推进；区分“对手机会质量恶化”和“实际失球高于对手xG”。
5. **攻防转换：** 得球后的推进与纵深出口、丢球后的恢复、反抢、IP↔OOP结构切换及空间保护；没有直接指标时明确写“未观测”，不得把推测写成事实。
6. **球员与位置：** 出场时间、每90分钟产量、效率、稳定性；只有身份、位置语义、逐场战术槽位和版本映射均可信时，才将表现归因到角色或PI。
7. **样本与质量：** 每个分组显示样本数；胜/平/负、主/客场、赛事、比分状态和对手强弱按报告能力分层。小样本只作提示。

必须沿“结果 → 机会质量 → 战术过程 → 配置”逐层诊断。每个主要问题写明：指标、样本、出现频率、影响范围、证据可信度、替代解释、问题级别（结构/协同/指令/执行）及优先级。不要罗列数据后不形成诊断。

战术评价不得使用犯规、黄牌、红牌作为优劣指标，也不得用纪律数据推动PI/TI调整。

## 4. 第二阶段：与整个项目总账联动（不能只看上一版）

必须读取并交叉核对：
- `TACTIC_INSTRUCTION_DECISION_LEDGER.md`：每条IP/OOP指令、角色、职责、PI、TI、结构组合的沿革、证据、状态和下一步。
- `VERSION_CATALOG.md`：所有版本赛季成绩、父子关系、recipe、构建身份、FMF哈希、D4/D5状态。
- `ITERATION_LOG.md`：完整历史问题、每轮决策、失败实验、未解决事项和结论变化。
- `SOURCE_REGISTER.md`：每份赛季报告的原始来源、Run ID、版本映射、build与数据状态。
- 当前唯一父版本的完整recipe、原生FMF、build request/build report、设计审计；最近D5分析及其原始报告。
- 历代重要赛季分析和曾经表现最佳/最差的版本，不得只读取最近两版。

总账比较要求：
- 同时识别历史综合最佳、进攻强项、防守强项、稳定性、主客场差异和结构性失败案例；不得把积分最高的版本自动当作所有方面最佳。
- 当前报告与历史版本尽量使用相同赛事、赛程范围和指标口径；覆盖率不同必须标明，不能直接比较不等量原始总数。
- 追踪某项配置何时引入、在哪些版本保留/改变、对应什么证据、后来是否被推翻；不得把相关性写成单项因果。
- 本轮父版本必须唯一且明确。父版本按项目当前正式版本链与用户确认的实测身份确定，不因某历史版本积分更高而擅自回退。
- 历史配方是证据和候选来源，不是必须继承的模板；不得机械复制旧版本或仅更改版本号。

## 5. 第三阶段：引擎红利资料库与外部实测研究

本阶段与赛季诊断联动，但不能只搜索支持当前初步想法的资料。每轮都要重新核对当前FM27 build，并继承、更新项目已有研究。

必须查阅：
- 项目完整引擎红利资料库及其索引、研究结论、待验证假设、适用条件和反例。
- `EXTERNAL_ENGINE_BENCHMARK.md` 及其中记录的FM-Arena、FMAX、metaFM当前build排名/测试快照。
- 爆棚及其他可信社区的FM27实测、机制讨论和版本更新反馈。
- 与本轮问题相关的外部战术原生FMF/完整配置；尽可能检查IP/OOP阵型、11槽/22阶段、角色、职责、PI、TI和转换，而非只看战术名称、阵型图或排名。
- 必要时检查补丁说明、游戏机制资料和原始测试协议，确认机制是否仍适用于当前build。

来源记录至少包括：URL、访问/快照日期、FM27 build、样本数量、测试协议、阵型阶段、关键发现、局限性及其对本轮设计的具体用途。
- FM-Arena、FMAX、metaFM等不同测试协议的数据必须分开呈现，不得简单相加或混成一个样本。
- 高排名三后卫/五后卫战术可以提供机制和结构启发，但不能作为本项目有球四后卫合规方案直接照搬；必须提取可迁移机制并重新设计。
- 无法取得原生FMF或完整配置时，只能记录页面可见信息，不得编造PI/TI或具体角色。
- 过期build、样本不足、协议不明或社区个例，必须降级为背景/假设，不能写成当前build已验证规律。
- 用户整理的机制线索（双阵型切换、无锋纵深、防线与压迫配合、个人逼抢分化、积极铲抢、远门柱传中、边后卫内收/套上/少射门、中卫短传/少射门、Step Up More / Drop Off More等）必须作为研究池逐项核对适用条件；不得只挑几条迎合本轮设计。

研究必须回答：哪些机制与本队本轮问题有关、外部证据支持到什么程度、哪些条件可能改变效果、哪些反例/风险存在、哪些需要本队赛季验证。

## 6. 第四阶段：四类决策与唯一整体战术重设计

在任何构建前，必须形成并写入本轮设计审计的四类决策：
- **继承保留：** 哪些历史配置/机制继续使用，依据是什么；区分“已准入”与“结构性暂留/单项未准入”。
- **替换淘汰：** 哪些配置退出本版，指出它在当前组合中的问题；不推导为该设置在所有位置/情境均无效。
- **新增待验证：** 新机制或配置组合、预期作用、主要风险、观察指标和D5验证方法。
- **证据不足：** 数据缺失、版本映射不明、外部证据过期、字段未解码或因果无法确认的事项。

然后选定并构建**唯一一套**最有依据的完整战术：
- 有球阶段唯一硬约束：后场四个位置槽必须是DL、DCL、DCR、DR。
- 不固定任何IP数字阵型；其余七个IP位置、角色、职责、PI、TI、心态完全开放。
- OOP阵型、人数、位置转换、角色、职责、PI、TI、心态完全开放，不要求与IP同形或保持四后卫。
- 不受现实足球理论限制；以FM27引擎表现和可核验证据为设计依据。
- 允许整体协同重构多个位置、角色、职责、PI、TI、心态；不以单变量实验或逐项独立证明作为升级前置条件。
- 每轮只向用户交付一个完整方案，不并行制作多套候选FMF。
- 必须检查11槽/22阶段完整配置、角色/职责合法性、PI权限、共享TI、心态、位置转换、原生字段和opaque字段。
- 每项重要变化必须关联本轮问题、历史证据、外部机制、预期收益、风险和D5观察指标。
- 心态是可调整变量，不是固定值；每轮必须重新评估，保持不变也要有设计理由。

## 7. 第五阶段：构建、验收、归档（同一轮完成）

完成设计后，在同一研发任务内继续：
1. 创建唯一子版本recipe/build request，记录唯一父版本、父FMF SHA、设计审计和四类决策。
2. 执行D1角色/职责/PI权限预检、D2 11槽/22阶段检查、D3原生FMF生成和独立回读。
3. 生成正式FMF及构建报告，记录Actions Run/Artifact、文件大小、FMF SHA-256、报告SHA-256和所有验证结果。
4. D3通过只表示离线文件生成/回读成功；不能声称游戏已导入或比赛表现有效。
5. D4只有在用户提供游戏内导入/显示证据并完成核对后才可标记通过；否则标记待用户验收。
6. D5只有收到该版本对应、用户确认映射的赛季报告后才可标记完成。
7. 同步更新 `TACTIC_INSTRUCTION_DECISION_LEDGER.md`、`ITERATION_LOG.md`、`VERSION_CATALOG.md`、`SOURCE_REGISTER.md`、本轮分析/审计/构建文件；不覆盖、不删除历史。
8. 写入后逐个GitHub read-back，核对文件内容、父子关系、版本、Run ID、Artifact、FMF与报告哈希、四类决策和D0–D5状态。read-back未完成不得声称归档完成。

## 8. 研发阶段状态与交付边界

每轮必须清楚记录以下状态：
- **D0：** 报告质量审计、赛季诊断、历史总账对比、引擎红利研究、四类决策和整体设计完成。
- **D1：** 原生角色/职责/PI权限及构建前置检查通过。
- **D2：** IP/OOP 11槽/22阶段、位置转换和结构检查通过。
- **D3：** 原生FMF生成、独立回读、哈希和构建报告完成。
- **D4：** 用户游戏内导入和显示确认。
- **D5：** 该版本正式比赛/赛季报告复盘完成。

本轮正常交付目标是D0–D3和唯一FMF。D4需要用户在游戏内操作，D5需要下一份赛季报告，二者不能虚报。完成D3后，本轮构建交付结束，等待用户导入、使用并提交下一份报告；下一份报告自动开启下一轮完整闭环。

## 9. 每轮结束前的强制自检

- [ ] 是否把报告分析、历史总账、外部研究和下一版设计放在同一轮，而不是分开结束？
- [ ] 是否读取完整总账和历史上有价值的版本，而非只看上一版？
- [ ] 是否核对完整引擎红利资料库及当前build外部实测？
- [ ] 是否明确用户确认的战术版本映射、数据质量和解析限制？
- [ ] 是否沿结果→机会→过程→配置诊断，并形成问题优先级？
- [ ] 是否完成继承保留、替换淘汰、新增待验证、证据不足四类决策？
- [ ] 是否仅设计一套完整战术，且IP后场四槽为DL/DCL/DCR/DR？
- [ ] 是否将所有分析结论转化为具体设计选择或明确说明为何不改？
- [ ] 是否完成D1–D3并核验正式FMF及SHA-256？
- [ ] 是否同步总账、版本目录、来源登记和迭代日志，并逐个read-back？
- [ ] 是否准确区分D3构建、D4游戏导入和D5赛季效果？

任何一项未完成，都必须如实标记未完成及原因，不得用“已分析”替代“已完成本轮研发”。
