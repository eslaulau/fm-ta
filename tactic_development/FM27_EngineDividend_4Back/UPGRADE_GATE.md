# FM27 EngineDividend 4Back｜研发闭环

> 本文定义实际研发顺序。项目已取消D0门禁；任何旧文档中的D0审批、机器清单或D0=BLOCKED规则均不再生效。

## 1. 输入确认
- 用户明确指定本轮实际使用的战术版本。
- 获取对应完整赛季报告及导出器数据质量说明。
- 核对样本是否为完整38场联赛；未完成赛季只作阶段性观察。
- 实际比赛战术映射以用户提供的信息为准，不允许导出器推断。

## 2. 赛季诊断
从结果到过程逐层分析：
1. 积分、胜平负、进球、失球、PPG、xG、xGA。
2. 机会数量与质量、射门转化、定位球和攻防转换。
3. 输球、平局及典型比赛；识别重复出现的问题。
4. 逐位置、逐角色、逐职责审查球员贡献与代价。
5. 与内部历史版本及历史配置进行横向比较。

缺失数据明确标记为缺失；不以单一统计指标直接认定某个角色有效或无效。

## 3. 内部历史总账
从 TACTIC_INSTRUCTION_DECISION_LEDGER.md 和 VERSION_CATALOG.md 检索相关内部版本。允许选择一个实际父版本，也允许组合多个历史版本的配置组件。记录父FMF路径、SHA-256、参考版本及选择理由。不得强制从V0.5重生，不得引入外部战术资料。

## 4. 新战术设计
每轮必须完整给出四类决策：
- 继承保留：有内部证据支持保留的配置。
- 替换淘汰：明确指出被替换的配置及原因。
- 新增待验证：新机制假设、预期收益、可能代价和可证伪指标。
- 证据不足：当前无法判断的配置及需要补充的数据。

形成唯一整体方案，说明IP结构、OOP固定位置下的角色协同、PI/TI组合和关键机制链。不得把历史战术原样复制为新版本。

## 5. 构建交付
按 GENERATION_EXECUTION_POLICY.md 完成原生权限预检、结构检查、FMF生成和独立回读。无需D0审计或机器决策门禁。交付FMF、recipe、构建报告、父版身份和哈希。

## 6. 游戏内与赛季验证
- D1：原生角色/职责/PI权限预检。
- D2：11槽/22阶段、固定边界及结构核验。
- D3：FMF生成与独立回读。
- D4：用户在游戏内导入并确认显示/配置正确。
- D5：使用该战术完成赛季并提交报告，验证积分和xG目标。

D1-D3不代表D4/D5成功。D4/D5未完成时保持待验证。

## 7. 每轮归档
同步更新 TACTIC_INSTRUCTION_DECISION_LEDGER.md、VERSION_CATALOG.md、ITERATION_LOG.md 和本轮设计/赛季报告。历史记录不删除；旧D0表述仅作为历史，不作为当前流程。
