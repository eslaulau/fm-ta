# FM27 引擎红利四后卫｜连续赛季研发闭环（最高执行入口）

> 本文件定义项目每一轮的实际工作流。用户提交一份新的战术赛季报告，默认意味着启动一轮完整的“赛季复盘 → 历史总账联动 → 引擎红利研究 → 整体战术升级 → FMF交付”任务；这不是几个可以彼此独立结束的任务。

## 0. 原始战术与历史范围

- **项目原始战术固定为 V0.5（V21 原生快照）。** V0.5 是唯一历史起点；所有历史总账、配方沿革、赛季比较、版本父子关系和后续升级均从 V0.5 开始。
- V0.5 之前的版本、配方、构建请求、赛季分析和审计不属于本项目资料，不得恢复、引用或作为战术设计证据。
- V0.5 的原始配置、FMF身份与赛季报告见 [V0.5_BASELINE.md](V0.5_BASELINE.md) 和 [V0.5_SEASON_REPORT_ANALYSIS_45540803100.md](V0.5_SEASON_REPORT_ANALYSIS_45540803100.md)。

## 1. 唯一研发循环

`用户提交新赛季报告 → 数据身份与质量核验 → 完整赛季诊断 → 历代总账联动 → 引擎红利与外部实测研究 → 四类决策 → 整体战术重设计 → 唯一FMF构建与核验 → 全部归档 → 等待下一份赛季报告`

- **报告是入口，FMF升级是本轮研发的交付终点。** 不得只完成报告分析后就把“是否升级”留给用户再次提出。
- 分析报告、总账对比、外部研究、设计审计、recipe、build request、FMF和构建报告必须属于同一轮、同一个版本链。
- 前一阶段的观察、证据、问题优先级和四类决策必须直接传递到下一阶段；不得在设计阶段重新开始、丢失或绕开分析结论。
- 新版本进入游戏后的表现，只有在用户提交下一份赛季报告后才能进入下一轮D5复盘。不得把构建成功误称为实战成功。
- 默认执行完整闭环。只有用户明确要求“仅分析/暂不升级/暂停”，或存在阻止继续的真实硬阻断，才可在中途结束。若受阻，必须说明具体缺口、已完成阶段、未完成阶段和恢复条件。

## 2. 输入、版本身份与数据质量

收到报告后，先识别并记录：
- Exporter Run ID、原始报告链接、存档标识/SHA（若提供）、FM27 build、导出器版本、报告日期。
- 用户确认的该报告实际使用战术版本及其 recipe/FMF/构建身份。
- 联赛、杯赛、洲际赛事及各自比赛数量；不得混合不同赛事口径。
- 球队统计、球员统计、身份匹配、位置/角色映射、统计对账、缺失/重复记录、解析器兼容状态。

版本归属规则：
- 只有用户明确确认的版本映射才可用于战术归因。文件名、最新构建版本、时间接近或助手猜测均不能代替确认。
- 若报告映射未确认：仍可完成报告本身的描述性数据审计和不依赖战术归属的统计分析；但必须把战术归因标记为“未确认”，并在无法确定父版本/当前战术身份时暂停生成升级FMF，直到身份得到确认。
- 数据覆盖不足不意味着整轮分析停止。应按可信层级继续：可用球队数据就分析球队层面；球员身份可靠才分析球员；位置、逐场槽位和角色映射可靠才归因到位置/角色/PI。缺失内容标为“未观测/证据不足”，不得补猜。
- 同一存档反复回滚测试、不同随机过程、共同赛程等情况必须按实际设计说明；非同seed比较不得写成受控A/B或单项因果证明。

## 3. 第一阶段：完整赛季报告诊断（D5复盘）

分析必须覆盖报告实际提供且语义可靠的全部关键领域：
1. **比赛结果：** 胜/平/负、积分/PPG、进失球、净胜球；分联赛/杯赛/洲际赛事，主场/客场。
2. **进攻：** xG/NPxG（注明口径）、射门与射正、绝佳机会、禁区威胁、创造与终结效率、实际进球相对预期的差额。
3. **推进与组织：** 后场出球、中场连接、向前传球/持球推进、进入前场三区和禁区、边中路供给与前场接应。原始次数应尽可能按每90分钟、控球或总传球量归一化。
4. **防守机会控制：** 对手射门/射正、绝佳机会、xG/xGA、禁区威胁、对手推进；区分“对手机会质量恶化”和“实际失球高于对手xG”。
5. **攻防阶段行为：** 得球后的推进与纵深出口、丢球后的恢复、反抢和空间保护；IP/OOP位置配对固定，只评估角色/职责/PI变化造成的阶段行为差异。没有直接指标时明确写“未观测”，不得把推测写成事实。
6. **球员与位置：** 出场时间、每90分钟产量、效率、稳定性；只有身份、位置语义、逐场战术槽位和版本映射均可信时，才将表现归因到角色或PI。
7. **样本与质量：** 每个分组显示样本数；胜/平/负、主/客场、赛事、比分状态和对手强弱按报告能力分层。小样本只作提示。

必须沿“结果 → 机会质量 → 战术过程 → 配置”逐层诊断。每个主要问题写明：指标、样本、出现频率、影响范围、证据可信度、替代解释、问题级别（结构/协同/指令/执行）及优先级。不要罗列数据后不形成诊断。

战术评价不得使用犯规、黄牌、红牌作为优劣指标，也不得用纪律数据推动PI/TI调整。

## 6. 第四阶段：四类决策与唯一整体战术重设计

然后选定并构建**唯一一套**最有依据的完整战术：

- 红框15项团队指令固定；心态固定为V0.5原生值4。

- 必须检查11槽/22阶段完整配置、三种IP布局之一、OOP V0.5固定位置映射、角色/职责合法性、PI权限、红框15项TI、29组TI覆盖、心态4、原生字段和opaque字段。
- 每项重要变化必须关联本轮问题、历史证据、外部机制、预期收益、风险和D5观察指标。
- 心态固定为V0.5原生值4，不得作为本轮搜索变量。

## 10. 赛季数据—历史总账—战术配置追踪规则（强制）

本节把赛季诊断与下一版战术配置连接起来，是D0设计审计的必备内容。**不允许只写“数据分析结论”与“新战术方案”两份互不对应的文档。** 每轮必须建立唯一的追踪矩阵，使用稳定的问题编号（例如 `ISS-01`）贯穿赛季分析、历史比较、外部研究、四类决策、recipe和下一轮D5复盘。

### 10.1 每个重要问题必须形成完整证据链

每个被列为主要问题/优势的条目，必须逐项记录：

1. **报告事实：** 指标定义、实际数值、样本数、赛事/主客场/胜平负/比分状态分组、与报告覆盖率和解析质量相关的限制。
2. **问题判断：** 这是结果问题、机会质量问题、战术过程问题，还是执行/球员条件问题；影响范围、频率、严重程度和优先级。
3. **替代解释：** 至少检查数据口径、样本波动、对手质量、比赛状态、阵容/球员可用性、临场事件、终结/门将偏差等报告可支持的替代因素。不能把所有赛季结果都归因于战术。
4. **历史对照：** 对照多个历史版本中同类表现最好和最差的样本，记录可比性、差异和相关配置沿革；不只看上一版，也不只选支持当前观点的版本。
5. **机制研究：** 关联引擎红利资料库和当前build外部实测中与该问题有关的机制、适用条件、反例和来源质量。外部机制必须解释“为何可能解决本队这个问题”，不能只因排名高就引用。
6. **配置落点：** 只可指向球员角色/职责、PI和非红框TI。IP阵型仅能在三种批准布局中选择；OOP位置映射、心态4及红框15项TI均固定。若数据不足以定位具体可调整项，明确停留在团队层，不得强行下钻。
7. **决策与变化：** 对应四类决策之一；若改动，写清父版本旧值→新值；若不改，写明保留理由或证据不足原因。
8. **预期与代价：** 预期改善的过程指标和结果指标、可能牺牲的优势、协同风险及观察方式。
9. **下一轮验证：** 指定下一份赛季报告要检查的指标、分组、比较基线、预期方向/目标区间和失败/回滚触发条件。没有可量化目标时，说明使用何种可观察证据。

重要问题不能在追踪矩阵中断链。若某个主要问题最终不引起配置变化，必须标注“本轮不改”并给出证据理由；不得静默遗漏。若某个重要配置变化没有对应的赛季问题，必须标记为“探索性引擎机制假设”，写明外部依据、风险和独立验证计划。

### 10.2 赛季报告必须分析输球、平局和典型比赛

在报告提供逐场数据的范围内，建立失利/平局案例清单，不得只用全赛季均值概括：
- 每场记录赛事、对手、主客场、比分、战术版本映射状态、我方/对手xG和绝佳机会等可用指标、比赛状态及数据完整性。
- 将案例归入进攻创造不足、机会转化偏差、推进/出球受阻、防守机会质量失控、转换暴露、领先/落后状态处理、阵容/球员条件或无法判定等类别。
- 找出重复出现的失败模式，并与胜场中的相似情境比较；单场异常只作为案例，不自动变成全局战术问题。
- 若缺少逐场报告或战术槽位映射，明确说明不能完成的层级；仍须完成赛季总体和可用分组分析。
- 犯规、黄牌、红牌不作为战术优劣指标，也不用于推导配置变化。

### 10.3 历史总账必须做多维基准，不得只按积分排序

每轮至少比较：
- 综合结果：完整联赛赛季积分、PPG、胜平负、进失球。
- 进攻：xG/NPxG、绝佳机会、射门/禁区威胁及创造效率。
- 防守：xGA、对手绝佳机会、对手射门质量及禁区威胁。
- 稳定性：主客场差异、表现波动、失利/平局模式和样本完整性。
- 结构经验：历史版本的IP/OOP结构、角色/职责、PI/TI、心态和已知组合结果。

标记各维度的历史强项、弱项和可比性。不得把积分最高版本自动定义为所有维度最优；不得将不同赛事、不同场次、不同build或覆盖率不同的原始总数直接排名。若样本不可比，降级为定性参考。

### 10.4 进攻、防守、推进、转换必须进行协同影响评估

任何设计决策都要检查对整体战术的连带影响，而不是按单个差指标逐项修补：
- 进攻产量与机会质量是否提升/下降；
- 推进、控球出口、进入危险区域的能力是否变化；
- 对手机会质量和禁区进入是否变化；
- 固定OOP位置映射下，角色/职责/PI切换如何影响丢球后保护、反抢和回收；
- 主客场、领先/平局/落后等情境是否可能出现相反效果。

当某项收益伴随另一项成本时，必须明确呈现收益—代价权衡。综合选择应结合项目目标、问题严重程度、历史多维表现、证据可信度和可接受风险；不得为方便而临时发明单一加权总分。若没有用户设定的权重，采用多维证据与Pareto式权衡，说明最终取舍理由。

### 10.5 区分战术结构、指令协同、球员执行与随机波动

每项诊断必须区分：
- **固定结构层：** IP只可选择4-2-3-1/4-3-3/4-1-2-3；OOP位置映射固定V0.5。两者均不是本轮可调整位置变量。
- **协同层：** 固定位置槽中的角色/职责行为、跑位、接应、压迫与保护关系。
- **指令层：** PI、TI、心态和具体行为触发。
- **指令层：** 个人指令PI和非红框团队指令TI的作用；红框TI及心态4固定。
- **执行层：** 球员属性、熟悉度、状态、可用性及实际执行。
- **结果波动层：** 终结、门将表现、样本随机性和比赛偶然因素。

不能仅凭球员赛季评分、进球数或单一总量就认定某个角色/PI有效或无效。球员身份、逐场槽位和字段语义不足时，只能在数据支持的较高层级提出假设。非同seed赛季之间不得写成单项因果证明。

### 10.6 设计目标必须在下一份报告中逐项回看

每轮D0必须生成“下一轮D5验证清单”，并将其同步到设计审计、迭代日志和版本目录。下一份报告到来时：

- 将有效结论沉淀到指令决策台账，修正被新证据推翻的旧结论；
