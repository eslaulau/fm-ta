# FM27 引擎红利四后卫｜仓库执行指令

本文件是每次任务的强制入口。**连续赛季研发流程以 `UPGRADE_GATE.md` 为最高执行规范**；`ANALYSIS_AND_ITERATION_RULES.md` 提供详细的数据分析、机制研究和战术设计规则。发生冲突时，采用用户最新明确要求及更严格的项目约束，并同步修正文档，不能自行挑选方便执行的旧规则。

## 用户提交赛季报告时的默认任务

用户提交新的FM27战术赛季报告，默认启动同一轮完整研发闭环，不需要用户再单独说“升级”：

`报告身份/质量核验 → D5完整赛季分析 → 历代总账联动 → 引擎红利资料库与当前build外部研究 → 四类决策 → 唯一整体战术重设计 → D1-D3构建并交付FMF → 更新归档 → 等待下一份报告`

不得把“分析报告”和“战术升级”拆成两个任务。分析发现必须直接进入升级决策；每条重要观察都要映射为继承、替换、新增待验证或证据不足的决定。只有用户明确要求仅分析/暂停，或真实硬阻断时才可不继续构建。

禁止只依赖聊天摘要、模型记忆或上一轮的简短结论。若资料库文件很多，先读取索引和目录，再按主题读取完整相关条目，并在本轮审计中列出实际读取的文件/来源；不得声称读过未读取的内容。

## 强制规则

- **唯一战术硬约束：** IP后场四个位置槽必须是DL、DCL、DCR、DR。不固定IP数字阵型；其余IP位置完全开放。OOP阵型、人数、角色、职责、PI、TI和转换完全开放。
- **目标是引擎收益：** 不以现实足球理论限制设计。
- **一个方案：** 每轮只选定、构建和交付一套完整战术，不向用户抛出多套候选让用户替研发做选择。
- **整体重设计：** 允许同时调整阵型、位置、角色、职责、PI、TI和心态；单变量实验仅为解决明确因果问题的辅助方式，不是默认升级门槛。
- **四类决策：** 每轮必须写明继承保留、替换淘汰、新增待验证、证据不足。
- **报告归属：** 只有用户确认的版本映射可用于战术归因。映射不明时可做描述性分析，但不能假定使用了哪个版本或据此生成错误的升级。
- **数据边界：** 不猜测缺失数据；球员/位置/角色归因必须满足身份和字段映射质量要求。不得用犯规、黄牌、红牌评价战术。
- **外部研究：** 记录URL、日期、build、样本量、协议、结构和局限；不同测试协议不合并。三后卫/五后卫排名仅用于提取机制，不能冒充本项目IP四后卫成品证据。
- **构建状态：** D3离线构建回读不等于D4游戏内导入，也不等于D5赛季有效。
- **归档：** 每轮同步更新 `TACTIC_INSTRUCTION_DECISION_LEDGER.md`、`ITERATION_LOG.md`、`VERSION_CATALOG.md`、`SOURCE_REGISTER.md` 和本轮分析/审计/构建文件；保留所有历史。
- **回读：** 每次写入后逐个重新读取GitHub文件，核对内容和哈希。read-back未完成不得声称写入成功。

## D0–D5状态定义

- D0：赛季报告数据审计、完整诊断、历史总账联动、外部机制研究、四类决策及整体设计。
- D1：角色/职责/PI权限及构建前置检查。
- D2：IP/OOP 11槽/22阶段与转换结构检查。
- D3：生成正式FMF、独立回读、哈希和构建报告。
- D4：用户游戏内导入/显示验收。
- D5：该战术版本对应的正式比赛/赛季报告复盘。

每轮交付目标为D0–D3；D4/D5未获得证据时保持pending。D3完成后等待用户使用战术并提交下一份报告，下一份报告自动启动下一轮闭环。
