# FM27 原生战术预设导出路线审计

日期：2026-11-17  
目标仓库：`eslaulau/FM27`  
审计对象：公开项目 `lqf0624/fm-tactics-lab`，v1114 源码  
用途：为本仓库十种官方风格的原生 FMF 模板补齐寻找可行的数据采集路径。

## 结论

**FM Tactics Lab 提供了比纯 Python 拆包更接近游戏原生加载流程的路线，但公开的 v1114 源码并没有现成的“批量导出所有内置 TAC/FMF”功能。**

它已经证明了两件事：

1. 原生宿主可以从本机 `shared/data/simatch.fmf` 绑定 FMF 资源，并调用游戏原生预设加载器，枚举已加载的风格对象和战术预设对象。
2. 项目有一个调用游戏原生战术序列化函数的 TAC 写出器，但现有实现导出的是**当前比赛对象某一侧的战术计划**，并非预设加载器中的全部原生预设。

因此不能把当前源码描述成已经能直接提供十种风格的原生 TAC 文件。本仓库此前的离线提取器仍是一个独立候选路线，必须以真实安装数据验证；原生宿主导出则是下一步值得实现的路线。

### `native_coach_presets.h` 的执行流程

- 由 `FM27_COACH_PRESET_EXPORT` 环境变量开启独立诊断模式。
- 将 `shared/data/simatch.fmf` 作为原生资源文件绑定到游戏 FMF 树。
- 调用原生 loader，枚举 style 对象并记录 style id/code。
- 遍历已加载 TAC 预设对象，读取预设名、style code、mentality、team instruction bytes、11 个槽位映射，以及 IP/OOP 每个槽位的位置、role flags 和 PI flags。
- 将合法阵型代码逐个交给原生阵型函数读取。
- 以 JSONL 诊断记录结束进程。

**重要：当前函数没有把这些 preset plan 逐份传给 TAC writer，也没有在此模式中输出原生 TAC 文件。** JSONL 字段适合做审计和交叉核对，但不等价于完整 TAC 二进制。

### `native_tactic_export.h` 的执行流程

- 由 `FM27_EXPORT_TAC` 开启。
- 从当前比赛对象的指定 side 找到 team/manager/plan。
- 可设置 plan 标题。
- 将该 plan 传入原生序列化函数 `at(0x1b8bfc0)`，使用有 4 MiB 上限的输出流。
- 写出单个 TAC 文件并记录 accepted、stream_error、size、side。

**重要：它当前的输入来自正在运行的 match 对象，不是 coach preset loader 的 preset 列表。** 不能直接声称它已经批量导出了原生预设。

## 下一步可实施的原生导出扩展

建议在独立诊断模式中新增一个明确的 `FM27_EXPORT_INSTALLED_PRESETS` 分支，复用已经成功加载的 preset loader：

1. 从 loader 的 preset 数组取得每个原生 plan 指针。
2. 对每个 plan 做边界检查：数组计数、指针范围、名称长度、style code、两个阶段各 11 个槽位。
3. 在副本上设置唯一导出标题，避免修改共享 loader 对象；如果无法安全复制，先只读调用并由 writer 单独承载标题，禁止直接改写游戏共享对象。
4. 将 preset plan 传入与 `native_tactic_export.h` 相同的原生 serializer 和有界 writer，逐个写出 TAC。
5. 每个文件写入 JSONL 收据：索引、原始名称、style code、字节数、SHA256、serializer accepted/error。
6. 任何失败都保留其他候选，并在总清单中明确失败原因；不以部分成功冒充完整覆盖。
7. 把 TAC 文件和清单交给本仓库 Python 工具：解析 TAC，核对 source-major、style string/code、11 组双阶段槽位、角色/职责与 PI 权限；再用已验证 FMF 外壳包装并回读。
8. 只有所有检查通过的风格才更新 `style_template_registry.json`。离线通过与游戏内导入/比赛验证必须分开标注。

### 必须先验证的技术风险

- preset loader 中的 plan 与 match manager 中的 plan 是否为同一种完整序列化对象；当前源码的偏移访问显示结构高度相似，但不能仅凭偏移推断 serializer 一定接受。
- serializer 是否要求 plan 已绑定某些 match、版本或资源上下文。
- 原生预设的 TAC style 字符串、四字节 code 和 PI cache 是否完整保存在该对象中，或有字段需要额外回填。
- preset loader 生命周期和资源对象引用计数；导出期间不得释放或修改共享资源。
- 上游适配器使用固定 RVA，依赖精确游戏构建和参考 DLL。不能把这些地址移植到其他 FM27 版本而不做兼容性检查。

## 当前执行边界

本次后台审计可以读取公开源码、检查结构并更新本仓库文档/工具，但无法远程访问用户电脑上的 FM27 安装目录，也无法从公开仓库取得用户本机的专有 `game_plugin.dll`、`simatch.fmf` 或真实游戏进程。因此：

- 不能在云端直接运行上游原生宿主来读取用户安装的预设。
- 不能声称已经生成八种缺失风格的真实 TAC/FMF。
- 不能声称已经完成 FM27 游戏内导入或比赛验证。
- 上游源码的 MIT 许可允许按许可证条件复用其代码；本仓库应优先复用技术接口/格式，若复制代码须保留相应版权和许可证声明。游戏资源和二进制不随 MIT 源码许可开放。

## 对本仓库当前方案的调整

- 保留现有 `FM27GEN1_Extract_Installed_Presets.py`，但将其定位为“待真实 simatch.fmf 验证的纯离线候选提取器”，不能作为已验证路径。
- 不再把上游 `native_coach_presets.h` 描述成已经具备 TAC 批量导出能力。
- 将“原生 loader 枚举 + 原生 serializer 批量导出”列为优先研究实现路线。
- 十种风格的正式支持仍由真实 TAC/FMF 回读、完整角色职责/PI 权限核验决定；当前只有 Gegenpress 和 Control Possession 保持已实现状态。

### 本轮补丁状态与限制

- 已提交的是**源码补丁草案**，不是已经应用到上游 FM Tactics Lab 的提交，也没有替换上游仓库文件。
- 尚未在 Visual Studio 编译，尚未在用户的 FM27 27.0.1 原生 DLL 上运行。

## 2026-11-17 路线调整：复用现有 FMF 原生回读链路（优先方案）

继续审计上游 Python 端后，发现比直接调用 loader plan serializer 更稳妥的现成路径：

1. \`src/desktop_coach_presets.py\` 的 \`assets()\` 已通过 \`FM27_COACH_PRESET_EXPORT\` 取得安装内全部 style rows 与 preset template rows；\`STYLE_NAMES\` 映射了 0–9 十种官方风格 ID，\`_style_candidates()\` 使用原生 style code 选择对应模板。
2. \`preset_by_index_team()\` 能按安装预设索引和模板 SHA256，把指定原生预设应用到战术板数据模型。
3. \`src/desktop_save_mode.py::preset_plan()\` 已调用 \`self.app.export_fmf()\` 走现有原生导出流程，再用 \`fm27_fmf.tactics_plan()\` 从输出 FMF 取回 TAC plan，并缓存。
4. \`src/desktop_save_mode.py::_league_export_row()\` 已用该计划配合 \`fm27_fmf.tactics_archive()\` 构造 FMF；因此无需向共享 loader 对象直接调用 C++ serializer，也无需改动原生 DLL。

上游 \`src/fm27_tactics_server.py::export_fmf()\` 的 \`native_roundtrip_verified\` 报告是在原生导出后再由原版解析器回读并比较关键战术字段。它比单纯 serializer accepted 或非空字节更强，但仍不是游戏界面导入/比赛验证。

### 旧方案处置

先前的 \`native_coach_presets.h\` 直接传 loader plan 给 \`at(0x1b8bfc0)\` 的 C++ 补丁草案已从本仓库删除，不再推荐。原因是它需要额外证明 loader 对象与 match plan 的 serializer 契约和副作用；现有 Python 导出链路已能通过原生 app exporter 实现相同目标，风险更低。

### 验收边界

- 新补丁只是上游源码补丁草案，尚未应用到上游、运行或测试。
- 导出成功的判据是每份文件的 \`native_roundtrip_verified=true\` 且 FMF 内 TAC 能完整提取；随后仍要由本仓库 \`FM27GEN1_StyleTemplate_Audit.py\` 解析并核验真实 style string/code、TI、22 个位置/角色/职责/PI 字段和权限。
- \`native_roundtrip_verified\` 不等于 FM27 游戏内导入成功；manifest 明确保留 \`game_import_verified=false\`、\`match_engine_verified=false\`。
- 上游 \`assets()\` 只证明其代码有十种 style ID 映射，不代表用户安装目录当前实际含有每种风格的模板。必须以本机运行导出的 catalog 和文件为准。
- 当前正式支持仍为 **2/10**。真实安装文件和原生导出结果尚未到达本仓库，不能增加支持数。
