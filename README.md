# FM27 战术生成规则

> **首次检索入口：** [00_资料总索引与检索规范.md](00_资料总索引与检索规范.md)。任何开发、生成、排查或资料搜索，先读总索引。不得只因单个目录或一次搜索没有命中，就声称角色、指令、风格资料缺失。

本目录采用唯一正式流程：战术设计 → 原生兼容核对 → 结构化 JSON 配方 → 离线原生 FMF 生成 → 独立回读 → 游戏内验收。正常“生成新战术”任务最终交付物必须是 FM27 原生 `.fmf` 文件；JSON 是正式输入，旧 GEN1 仅保留兼容读取。

## 全仓库战术使用政策（最高优先级）

**本仓库没有任何推荐战术，也没有任何经本项目确认的成功战术。仓库内所有战术文件一律不得作为新战术开发参考。**

此规则覆盖全仓库，不因文件名称、来源、风格、历史版本或文件是否通过某种测试而例外，包括但不限于：

- 所有 FMF 战术文件、原生风格样本和生成器参考文件；
- 所有 GEN1 配方、历史战术方案、研发版本和离线重建文件；
- 网站索引中的 90 条预设、额外辅助模板及教练模板；
- 任何被称作 sample、template、preset、reference、rebuild 或历史版本的战术配置。

**禁止**将上述文件中的阵型、IP/OOP 角色、职责、球员指令（PI）、球队指令（TI）、攻防转换、压迫结构或整套配置复制、拼接、改名、微调后作为新战术；也禁止把它们作为种子、基准、优化方向、推荐对象、成功案例或性能证据。不得因为文件存在、生成成功、离线回读通过、通过 CI，或来自网站“官方预设”索引，就推断其战术效果优秀。

新战术必须根据用户当前目标和真实比赛数据独立设计。只有完成明确、统一条件且有充分样本的实战测试，才可评价该次新战术的表现；不能把测试结论外推到仓库里的其他文件。

**技术用途例外仅限文件格式层面：** 为维护解析器/生成器，必要时可以读取原生文件的容器结构、字段编码、style code、位置/角色 ID 和二进制兼容信息；这不构成战术开发参考许可。不得把技术模板中原有的战术配置当作设计依据。为兼容格式而不得不保留的未知/opaque 字节，只能标记为格式兼容数据，不能解释为推荐战术设置或效果证据。

## 战术创新原则（必须积极执行）

上述禁止复制和改造仓库现存战术的规则，目的是消除路径依赖，**不是限制创新**。本项目必须积极鼓励原创战术设计：

- 从用户当前目标、球队球员特点、真实比赛数据和对手问题出发，从零提出战术解法；不得先挑一个旧战术再做局部修改。
- 鼓励探索全新的攻防结构，包括但不限于非对称 IP/OOP 阵型、不同阶段的角色与职责重组、全新的 PI/TI 协同、压迫与回撤结构、攻防转换方式，以及不依赖单一传统风格的混合思路。
- 不受仓库现有战术文件、90 条网站预设、历史配方、模板或十种风格名称的战术思路限制。十种风格及其 style code 只是目前掌握的原生文件身份/格式兼容资料，不是必须遵循的战术蓝图，也不代表只有这十种战术思路才可创新。
- 如果当前 FMF 生成链路要求选择已登记的原生 style code 或技术模板，只能把它们作为文件序列化和兼容性载体；实际阵型、角色、职责、PI、TI 与整体攻防逻辑仍须独立原创，不能继承模板原有战术配置。
- 创新方案必须符合 FM27 当前可验证的位置、角色、职责、PI/TI 写入权限和文件格式约束。超出现有映射的想法应明确标记为待研究/待实现，不得静默降级或假装已经支持；通过 D4 游戏内验收和 D5 统一条件实战验证后，才能评价其可用性和效果。

**研发方向：不寻找旧战术的改良版，而是提出新的战术解法，再用真实比赛数据验证、迭代。**

## 2. 当前风格支持基线

当前分支已登记十种官方风格的原生 TAC 字符串、四字节 style code 和模板路径，并完成十种模板的离线结构生成/回读测试：

Catenaccio、Control Possession、Direct Counter Attack、Fluid Counter Attack、Gegenpress、Park The Bus、Route One、Tiki-Taka、Vertical Tiki-Taka、Wingplay。

具体样本与模板对应关系只以 `04_离线原生FMF生成器/style_template_registry.json` 为准。特别注意：`1.fmf` 是 Control Possession 原生样本，但由于其 AOM 标题 token 重复，安全模板使用 `123_Game_Export_Reference.fmf`；不能把这误判为缺少第一种风格。


## 样本使用边界：A9.0.2 不是成功战术

仓库中的 `FM27_A9.0.2_GEN1.txt`、`FM27_A9.0.2_Offline_Rebuild.fmf` 和对应 report 只作为历史技术工件保存。它们证明的是当时的 GEN1→FMF 离线转换与二进制回读，不是完整赛季战术表现证据。

**不得把 A9.0.2 当作成功案例、推荐战术、默认生成模板、优化起点或其他战术的设计基准。** 它没有完成完整赛季成功验证；对应报告中的 `game_interactive_import=false`、`match_engine=false` 也明确表示没有游戏内导入与比赛引擎证据。除非用户明确要求检查这份历史文件，否则生成新战术时应从用户当前目标、完整比赛数据、原生权限资料和十种原生风格证据独立设计，不能因 A9.0.2 曾被生成就复制其阵型、角色或指令。

## 3. 默认交付合同（必须执行）

用户提出“生成新战术”“做一套战术”“优化后给我战术”等请求时，默认交付：

1. **必交：** 本次实际生成的原生 `.fmf` 文件。
2. **必交：** 与该 FMF 同次生成的 `.report.json` 独立回读报告。
3. **辅助留档：** 对应结构化 JSON 源配方可一并提供，便于复现和审计；旧 GEN1 TXT 不是新流程的必需文件。
4. **说明：** 简要列出阵型、战术设计要点、数据依据及尚未验证的限制。

只输出设计说明、JSON 配方或运行命令，均不算完成战术生成；必须实际生成并检查 FMF。若生成器没有实际成功运行，必须明确报告失败/阻塞原因，不得用 GEN1 冒充 FMF。

## 4. 唯一正式生成流程

1. **读取与分析。** 先读 00 总索引，再查对应的预设、位置、球员与比赛资料；明确数据范围和缺失项。
2. **战术设计。** 确定 IP/OOP 阵型、11 个槽位、22 个阶段角色、duty、PI 和球队 TI。
3. **原生兼容核对。** 用第 02 层目录按 phase、position、role ID、duty 核对每条 PI；位置别名只用于规定的查询/规范化路径。
4. **生成并预检 JSON。** 输出完整 UTF-8 战术对象，检查根字段、11 槽位、双阶段位置、角色/duty 映射及 PI/TI 映射；不进行 GEN1 Base64 包装。
5. **实际生成 FMF。** 调用第 04 层离线生成器，传入本次配方、catalog 和风格注册表，按风格自动选择已登记模板。
6. **独立回读。** 检查 FMF/TAC 容器、11 组 IP/OOP、22 阶段位置/角色/duty/PI mask、TI 向量及成员长度。
7. **交付。** 提供本次实际生成的 `.fmf` 和对应 `.report.json`。
8. **游戏内验收。** 在 FM27 导入、逐项检查、保存、关闭并重新打开。只有通过才是 D4。
9. **实战验证。** 统一条件比赛测试通过后才是 D5。

详细步骤见 [离线生成流程](04_离线原生FMF生成器/FM27GEN1_离线原生FMF_生成流程.md) 和 [字段契约](04_离线原生FMF生成器/FM27GEN1_离线原生FMF_字段契约.md)。

## 5. 个人指令完整性规则

正式战术生产要求 22/22 个阶段都明确设计个人指令：

1. 每个阶段必须有 `pi` 字段；正式交付验收要求每个阶段至少有一条有效 PI。
2. 每条 PI 必须按 phase、原生位置上下文、角色 ID 和 duty 查第 02 层权限数据。
3. 固定开启、固定关闭、不可用选项不得冒充可编辑 PI。
4. 当前 `PI_MAP` 只包含已经建立原生 option ID 映射的子集；有权限记录但尚未建立写入映射的选项，不可猜测写入。
5. 如果所需 PI 尚未映射，应先根据原生证据补充映射和测试；如果角色确实没有合适可编辑 PI，应更换角色/位置方案。
6. 生成器源码当前要求 `pi` 字段存在并验证数组中的选项，但空数组在结构层面仍可通过。因此，**正式战术的 22/22 非空 PI 是项目交付验收规则，不应误说成生成器已经自动强制非空。**

权限数据已经存在，不代表所有 PI 选项均已进入写入映射。参阅 00 总索引的“指令资料准确范围”。

## 6. 当前实现边界（必须如实描述）

- 十种风格：已登记原生样本、style code 和模板；十风格离线结构生成/回读烟雾测试通过。
- 角色：62 个网站显示名索引、79 个原生阶段角色 ID、位置资格数据均已存在；生成器角色别名和 `ROLE_DUTY` 映射以源码为准，不能假设 79 个角色的所有 duty 组合均已穷举。
- PI：原始权限数据、STC 扩展和 catalog policy 数据均已存在；当前生成器只写入 `PI_MAP` 支持的选项子集。
- TI：十种风格的默认心态/TI 参考配置已保存；实际写入只接受 `TI_GROUPS/TI_MAP` 已映射项，未声明项由模板继承或按规则拒绝。
- TI 是单一共享 12 字节向量，不存在独立 IP/OOP 两套向量。
- 原生 JSON 的阶段对象可选写入 `duty`；73 个角色可沿用有证据的默认值，其余 6 个角色必须显式指定 D/S/A 或原生 duty bit。
- 当前十风格端到端烟雾测试使用 `pi: []`、`ti: {}`，证明十种模板路径能生成并回读，不证明所有 PI/TI 选项组合都已测试。
- 离线结构回读成功不等于 FM27 客户端已导入、保存、重开或比赛实测成功。

**禁止再使用“只支持 Gegenpress 风格”作为当前分支描述。** 该说法属于旧版字段文档，现已由十风格注册表和本文件更新替代。

## 7. 现有战术优化规则

当用户提供现有战术及比赛、球员或位置表现数据并要求优化时，必须主动落实改动，而不只给评价：

- 逐位置结合评分、进球/助攻、抢断/拦截/夺回球权、传中/关键传球/创造机会等可用指标判断 IP/OOP 角色是否合理。
- 保留表现优秀且与整体打法一致的位置；优先修复反复暴露的弱势位置。
- 被调整位置必须同步检查 IP/OOP 角色和 PI；每项改动说明数据问题、战术原因和预期改善方向。
- TI 优化必须基于整体攻防表现，并遵守单一共享向量和当前映射范围。
- 数据缺失要明示，不得虚构；样本不足要说明置信度。
- 最终按本目录正式流程生成 FMF 并提供回读报告。未生成真实 FMF 就不能说优化交付完成。

## 8. 验收等级

- D0：战术设计完成。
- D1：原生角色、位置、duty 与 PI 静态权限核对完成。
- D2：结构化 JSON 与 11 槽结构预检通过。
- D3：本次 FMF 已生成，离线 FMF/TAC 及源码覆盖范围内字段回读通过。
- D4：FM27 内加载、核对、保存、关闭并重新打开成功。
- D5：统一条件下完成比赛验证。

普通新战术至少完成 D3。只有 D4 才能称“游戏内可用”；只有 D5 才能评价实战效果。原始权限 CSV、HAR、原生 FMF 样本和历史报告必须保留；派生数据必须标明来源。
